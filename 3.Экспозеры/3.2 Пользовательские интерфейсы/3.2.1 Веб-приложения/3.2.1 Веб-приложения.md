# 3.2.1 Веб-приложения

## 3.2.1.0 Введение
Веб-приложения на сегодняшний день являются наиболее распространенным типом компонентов-экспозеров. Их гораздо проще использовать, чем другие известные UI-компоненты в индустрии ПО. Рынок веб-технологий также гораздо доступнее для инженеров в плане публикации и обновления по сравнению с мобильными приложениями, что делает его привлекательным для начинающих специалистов. Но что еще важнее, веб-приложения обладают гораздо более разнообразным набором технологий, чем мобильные приложения.

В этой главе для демонстрации реализации принципов Стандарта в веб-приложениях будет использоваться технология Blazor. Однако, как упоминалось ранее, Стандарт независим от технологий, что означает возможность его применения к любому веб-стеку без каких-либо проблем.

Как показано выше, веб-приложения похожи на основные API, за исключением того, что они имеют другую группу компонентов в плане визуализации, таких как Страницы (Pages), Компоненты (Components) и Основы (Bases). В каждом веб-приложении пересекаются два основных потока: поток представления (presentation flow) и поток данных/бизнеса (data/business flow). В зависимости от того, где веб-приложение находится с точки зрения высокоуровневой архитектуры, его расположение определяет, является ли его бэкенд (BFF или Backend of Frontend) бизнес-потоком или просто потоком данных. Давайте обсудим эти детали в разделе «Характеристики».

## 3.2.1.2 Характеристики
Брокеры, Сервисы, View-сервисы, Основы (Bases), Компоненты и Страницы. Веб-приложения обычно состоят из шести основных компонентов. Поскольку мы уже обсуждали компоненты потока данных в разделе «Сервисы», в этой части мы сосредоточимся на аспекте UI (Bases, Components и Pages) с небольшим дополнением о view-сервисах.

Давайте обсудим эти характеристики здесь.

### 3.2.1.2.0 Анатомия
UI-компоненты состоят из базовых компонентов (base components), основных компонентов (core components) и страниц (pages). Все они разделяют ответственность за интеграцию, рендеринг и маршрутизацию пользователей к определенной функциональности интерфейса. Эти компоненты организованы в каталоге `Views` в четкой, предметно-ориентированной структуре (domain-driven) для упрощения навигации, обеспечения согласованности и масштабируемости. Структура папок выглядит следующим образом:

- **Views**
  - **Bases**: Содержит базовые компоненты, которые абстрагируют нативные или сторонние элементы.
  - **Components**: Включает классифицированные UI-компоненты (Foundations, Processings, Orchestrations, Aggregations).
  - **Pages**: Представляет страницы, с которыми взаимодействует конечный пользователь.

Давайте подробно обсудим эти типы.

#### 3.2.1.2.0.0 Базовый компонент (Base Component)
Базовые компоненты подобны брокерам. Это обертки вокруг нативных или внешних UI-компонентов. Их основная обязанность — абстрагировать любую жесткую зависимость от не-локальных возможностей интерфейса. Например, если мы хотим предоставить возможность создания текстовых полей для ввода или захвата данных, нативный тег `<input>` может обеспечить эту возможность. Однако прямое использование этого тега в наших основных UI-компонентах опасно, так как создает жесткую зависимость от неабстрактных компонентов интерфейса. Если позже мы решим использовать другую стороннюю библиотеку, нам придется менять нативные теги `<input>` во всех компонентах, где они используются, что не является оптимальной стратегией.

Основы (Bases) организованы в каталоге `Views/Bases`, при этом каждый базовый компонент находится в папке, специфичной для своей области. Например:
- `Views/Bases/Buttons/ButtonBase.razor`
- `Views/Bases/Toasts/ToastBase.razor`
- `Views/Bases/Divisions/DivisionBase.razor`

Как видно из приведенного выше примера, базовые компоненты оборачивают внешний или нативный UI-компонент, а затем предоставляют API для беспрепятственного и программного взаимодействия с ним. Иногда эти API представляют собой параметры, функции или делегаты для взаимодействия с компонентом в соответствии с бизнес-процессом.

##### 3.2.1.2.0.0.0 Реализация
Давайте рассмотрим простой базовый компонент для решения этой задачи:

```html
<input @bind-value=Value />
```

```csharp
public partial class TextBoxBase : ComponentBase
{
    [Parameter]
    public string Value {get; set;}

    public void SetValue(string value) =>
        this.Value = value;
}
```

В приведенном выше коде мы обернули тег `<input>` нашим базовым компонентом `TextBoxBase` и предоставили входной параметр `Value`, который передается в нативный UI-элемент. Кроме того, мы создали публичную функцию `SetValue`, позволяющую программно имитировать поведение пользователя для тестирования компонента, потребляющего этот базовый элемент.

##### 3.2.1.2.0.0.1 Использование
Теперь, когда нам нужно использовать этот базовый компонент на уровне основных компонентов, мы вызываем его следующим образом:

```html
<TextBoxBase @ref=MyTextBox />
```

Атрибут `@ref` позволит коду бэкенда программно взаимодействовать с базовым компонентом «за кулисами» для вызова любой существующей функциональности.

##### 3.2.1.2.0.0.2 Ограничения
Компоненты могут использовать только базовые компоненты. Страницы не могут их использовать, и другие базовые компоненты также не должны их использовать. Что еще более важно, предпочтительно, чтобы базовые компоненты оборачивали один и только один не-локальный компонент.

Как и Брокеры, базовые компоненты не содержат бизнес-логики. Они не обрабатывают исключения, не производят расчеты и не выполняют никакую последовательную, итеративную или селективную бизнес-логику. Эти операции либо основаны на данных (принадлежат view-сервисам и нижестоящим API), либо на UI (принадлежат основным компонентам).

Базовые компоненты также не обрабатывают исключения, не выбрасывают собственные исключения и не выполняют никаких валидаций.

#### 3.2.1.2.0.1 Основной компонент (Core Component)
Основные компоненты подобны сервисам в потоке данных. Они разрабатываются через тестирование (TDD) и ограничены одной зависимостью в любой момент времени. Основные компоненты используют базовые компоненты для реализации конкретного бизнес-процесса. Они менее универсальны, чем базовые, потому что оркестрируют и взаимодействуют с очень конкретным сервисом для потока данных.

Компоненты организованы в каталоге `Views/Components`, далее классифицированном по типам: Foundations (фундаментальные), Processings (обрабатывающие), Orchestrations (оркестрирующие) и Aggregations (агрегирующие). Каждый компонент находится в папке, специфичной для предметной области, с именем файла, включающим категорию (за исключением Foundations). Например:
- `Views/Components/Foundations/Subscriptions/SubscriptionsComponent.razor`
- `Views/Components/Processings/UserGrids/UserGridsProcessingComponent.razor`
- `Views/Components/Orchestrations/GroupDialogs/GroupDialogsOrchestrationComponent.razor`

Основные компоненты являются оркестраторами UI и данных. Они задействуют один или несколько базовых компонентов для построения бизнес-процесса (например, формы регистрации студента), затем отправляют сигнал view-сервисам для сохранения данных и возвращают ответы или сообщают об ошибках.

Основные компоненты состоят из трех основных частей: Элементы (Elements), Стили (Styles) и Действия (Actions). Давайте обсудим эти части.

#### 3.2.1.2.0.1.0 Элементы (Elements)
Элементы — это в основном фрагменты разметки, которые вы находите в файле `.razor` любого компонента. Этими элементами всегда должны быть базовые компоненты. Они являются «скелетом» любого основного компонента. Элементы могут предоставлять или не предоставлять подпрограммы, такие как клик кнопки (Button Click), или реактивные подпрограммы, такие как изменение цвета кнопки при наведении (hover), и так далее.

Элементы можно тестировать тремя основными способами: Существование (Existence), Свойства (Properties) и Действия (Actions).

#### 3.2.1.2.0.1.0.0 Существование (Existence)
Прежде всего, нам нужно убедиться, что элемент загружен и присутствует на экране. Это может быть сделано тремя способами: через привязку свойства (property assignment), поиск по ID или поиск по типу. Вот несколько примеров:

#### 3.2.1.2.0.1.0.0.0 Привязка свойства (Property Assignment)
Каждый компонент должен иметь соответствующее свойство, связанное с элементом во время выполнения. Например, предположим, что у нас есть `StudentRegistrationComponent`:

```csharp
public class StudentRegistrationComponent: ComponentBase
{
    public TextBoxBase NameTextBox {get; set;}
}
```
В приведенном выше коде мы определили `NameTextBox` того же типа, что и базовый компонент, который будет к нему прикреплен. Как только это свойство определено, нам нужно написать падающий тест, проверяющий существование этого элемента:

```csharp
public void ShouldLoadNameTextBox()
{
    // when
    this.renderedStudentRegistrationComponent =
        RenderComponent<StudentRegistrationComponent>();

    // then
    this.renderedStudentRegistrationComponent.Instance.NameTextBox
        .Should().NotBeNull();
}
```

Этот тест упадет, потому что на момент рендеринга никакая разметка не соответствует свойству `NameTextBox`. Давайте заставим тест пройти, изменив разметку в `StudentRegistrationComponent.razor`:

```html
<TextBoxBase @ref=NameTextBox>
```
Теперь тест пройдет, так как свойство динамически инициализируется во время рендеринга при загрузке страницы.

#### 3.2.1.2.0.1.0.0.1 Поиск по Id
Иногда привязка свойства невозможна. Существуют сценарии, когда компоненты динамически загружают набор вложенных компонентов, к которым у нас может не быть доступа на этапе проектирования. В этом случае поиск по ID является лучшим вариантом для получения нужного компонента.

Пример: предположим, у нас есть список компонентов, который загружается динамически на основе списка студентов. Мы используем `Id` объекта студента в качестве идентификатора для каждого компонента. Код выглядит следующим образом:

```csharp
public partial StudentListComponent : ComponentBase
{
    public List<Student> Students {get; set;}

    ....

    public void OnInitialized() =>
        Students = await this.someStudentViewService.RetrieveAllStudentsAsync();
}
```
При загрузке мы асинхронно вызываем view-сервис для получения списка всех студентов. Нам нужно взять этот список и динамически загрузить вложенное представление для каждого студента. Сначала напишем падающий тест:

```csharp
public void ShouldLoadStudentsAsync()
{
    // given
    List<Student> randomStudents = CreateRandomStudents();
    ...

    this.someStudentViewService.Setup(service =>
        service.RetrieveAllStudentAsync())
            .ReturnsAsync(randomStudents);

    // when
    this.renderedStudentListComponent =
        RenderComponent<StudentRegistrationComponent>();

    // then
    ....

    foreach(Student student in randomStudents)
    {
        StudentComponent studentComponent =
            this.renderedStudentListComponent.Find($"#{student.Id}")
                as StudentComponent;

        studentComponent.Should().NotBeNull();
    }
    
    ...
}
```

В этом тесте мы искали компоненты, соответствующие `ID` студента, и проверяли их существование. Сделаем тест успешным:

```html
<Iterations Items="Students">
  <StudentComponent Value="@context" />
</Iterations>>
```

Мы используем библиотеку `PrettyBlazor`, чтобы разметить поведение итерации с помощью тега `<Iterations>`. Теперь наши тесты должны проходить, находя и проверяя каждый созданный компонент после его загрузки на экран.

#### 3.2.1.2.0.1.0.0.2 Общий поиск
Бывают ситуации, когда у нас нет ключа или `ID` для поиска элемента. Мы ожидаем, что на экране загрузится список «чего-то» без данных или информации о них. В этом случае нам придется прибегнуть к механизму общего поиска, где мы полагаемся на количество отрисованных компонентов в сравнении с ожидаемым количеством:

```csharp
public void ShouldLoadManyElements()
{
    // given
    int randomCount = GetRandomNumber();

    // when
    this.renderedThingsComponent =
        RenderComponent<StudentRegistrationComponent>();

    // then
    var renderedThings = this.renderedThingsComponent.Find("p");

    renderedThings.Count.Should().Be(randomCount);
}
```

Стандарт не рекомендует загружать на экран компоненты с неизвестным типом, так как это дает инженерам гораздо меньше контроля над происходящим. Но в игровых сценариях это может быть единственным вариантом.

#### 3.2.1.2.0.1.0.1 Свойства (Properties)
Другой аспект, который мы учитываем при разработке основных компонентов — это их свойства. Это могут быть свойства самого основного компонента или базового компонента. Например, мы хотим убедиться, что компонент `LabelBase` имеет информационное свойство, такое как «Имя» (First Name) или «Фамилия» (Last Name).

Начнем с настройки теста.

```csharp
public class StudentRegistrationComponent: ComponentBase
{
    public LabelBase FirstNameLabel {get; set;}
}
```

В приведенном выше коде наш компонент регистрации студентов имеет на экране метку, которая по умолчанию должна иметь определенное значение для формы. Напишем для неё падающий тест:

```csharp
public void ShouldHaveFirstNameLabel()
{
    // given
    string expectedFirstNameLabel = "Имя";

    // when
    this.renderedStudentRegistrationComponent =
        RenderComponent<StudentRegistrationComponent>();

    // then
    ...\
    this.renderedStudentRegistrationComponent.Instance.FirstNameLabel.Value
        .Should().Be(expectedFirstNameLabel);

    ...
}
```

Этот тест проверит, что метка всегда будет иметь значение свойства «Имя». Сделаем его успешным:

```html
<LabelBase @ref=FirstNameLabel Value="Имя">
```
Таким образом, мы убедились, что элемент существует с правильным свойством или информацией.

То же самое относится и к свойствам самого основного компонента, таким как вью-модели, которые загружаются при инициализации и затем назначаются определенным базовым компонентам. Мы покажем этот пример чуть позже.

#### 3.2.1.2.0.1.0.2 Действия (Actions)
Тестирование действий — одна из важнейших частей тестирования любого элемента. Мы хотим убедиться, что определенное действие срабатывает при клике на кнопку. Эти действия также могут изменять свойство, создавать новый элемент или запускать другое действие. Возможностей здесь столько же, сколько в самом паттерне Тройственности (Tri-Nature).

Предположим, наш `StudentRegistrationComponent` должен инициировать вызов `StudentViewService` при клике на кнопку. Начнем с простого падающего теста:

```csharp
[Fact]
public void ShouldSubmitStudent()
{
    // given
    StudentView randomStudentView = CreateRandomStudentView();
    ...

    // when
    this.renderedStudentRegistrationComponent =
        RenderComponent<StudentRegistrationComponent>();

    this.renderedStudentRegistrationComponent.Instance.SubmitButton.Click();

    // then
    this.studentViewServiceMock.Verify(service =>
        service.AddStudentViewAsync(
            this.renderedStudentRegistrationComponent.Instance.StudentView),
                Times.Once);

    ...
}
```

В этом тесте мы предлагаем реализовать компонент, который при клике на кнопку запустит `AddStudentViewAsync` из `StudentViewService`. Это подразумевает корреляцию между кликом кнопки и запуском действия.

Напишем реализацию этого поведения. На стороне кода компонента должна быть следующая функция:

```csharp
public partial class StudentRegistrationComponent : ComponentBase
{
    [Inject]
    public IStudentViewService StudentViewService { get; set; }
    ...
    public StudentView StudentView { get; set; }
    public ButtonBase SubmitButton { get; set; }
    ...

    public async void RegisterStudentAsync() =>
        await this.StudentViewService.AddStudentViewAsync(this.StudentView);
}
```

Этот код реализует функцию `RegisterStudentAsync`, которая передает данные свойства `StudentView` в `StudentViewService` для регистрации. Теперь привяжем эту функцию к UI-элементу на стороне разметки:

```html
<ButtonBase @ref=@SubmitButton
            Label="ОТПРАВИТЬ"
            OnClick=@RegisterStudentAsync />
```

В разметке мы привязали свойство `SubmitButton` к элементу и передали событие `OnClick` с подпрограммой `RegisterStudentAsync`. При клике на кнопку эта подпрограмма сработает, и мы сможем подтвердить это в наших юнит-тестах.

#### 3.2.1.2.0.1.1 Стили (Styles)
Основные компоненты несут в себе больше, чем просто элементы. Они обладают определенными стилями, чтобы пользовательский опыт соответствовал типу бизнеса, который они пытаются реализовать. Хотя элементы или базовые компоненты также могут иметь свои собственные стили, важно понимать, что стили лучше подходят для основных компонентов, чтобы обеспечить модульность базовых компонентов для соответствия любому стилю, заданному основными компонентами.

Тестирование стилей редко встречается в мире UI. Особенно когда речь идет о разработке стилей на языке C# в виде кода. Стандарт продвигает идею использования (по возможности) одного и того же языка программирования для всех аспектов проекта. Это включает инфраструктуру, пайплайны, стили, действия и все остальное между ними. Этот принцип гарантирует, что кривая обучения для инженеров, работающих над любым проектом, будет минимальной, в дополнение к наличию стандартизированных паттернов.

Мы будем использовать библиотеку SharpStyles для тестирования стилей в основных компонентах. Эта библиотека безупречно транслирует код C# в стили CSS.

Рассмотрим сценарий, в котором мы хотим, чтобы наша кнопка `SubmitButton` в компоненте регистрации имела синий фоновый цвет. Добавим свойство `Style` в наш компонент:

Сначала нам нужно создать C#-модель с идентификаторами, которые мы хотели бы иметь в нашем CSS-стиле:

```csharp
public class StudentRegistrationStyle : SharpStyle
{
    [CssClass]
    public SharpStyle SubmitButton { get; set; }
}
```

Эта модель будет переведена в CSS-класс с именем `submit-button` при рендеринге компонента. Используем эту новую модель в нашем компоненте:

```csharp
public partial class StudentRegistrationComponent : ComponentBase
{
        public StyleBase StyleElement { get; set; }
        public StudentRegistrationStyle StudentRegistrationStyle { get; set; }
        ...
}
```

Теперь, когда у нас есть новое свойство для стилей, нам нужно подключить его к разметке, которая трансформирует эти стили/модели в чистый нативный CSS. Нам понадобится создать элемент `StyleBase` или базовый компонент, который возьмет на себя абстракцию, чтобы у нас не было жесткой зависимости от библиотеки SharpStyles:

Разметка этого элемента будет выглядеть так:

```html
<style>
    @Style.ToCss()
</style>
```

Код этого же элемента/базового компонента:

```csharp
public partial class StyleBase : ComponentBase
{
    [Parameter]
    public SharpStyle Style { get; set; }
}
```

Теперь используем этот базовый компонент в нашем `StudentRegistrationComponent`:

```html
<StyleBase @ref=StyleElement
           Style=StudentRegistrationStyle />
```

Теперь всё готово, напишем падающий тест, требующий, чтобы у кнопки был синий фоновый цвет:

```csharp
[Fact]
public void ShouldRenderContainerWithStyles()
{
    // given
    string expectedCssClass = "submit-button";
    ...
    var expectedStyle = new StudentRegistrationStyle
    {
        SubmitButton = new SharpStyle
        {
            BackgroundColor = "blue"
        },
    };

    // when
    this.renderedStudentRegistrationComponent =
        RenderComponent<StudentRegistrationComponent>();

    // then
    this.renderedLabOverviewComponent.Instance.SubmitButton.CssClass
        .Should().BeEquivalentTo(expectedCssClass);

    this.renderedStudentRegistrationComponent.Instance.StudentRegistrationStyle
        .Should().BeEquivalentTo(expectedStyle);

    this.renderedStudentRegistrationComponent.Instance.StyleElement.Style
        .Should().BeEquivalentTo(expectedStyle);
}
```

С таким падающим тестом мы можем приступить к реализации:

На стороне кода компонента сгенерируем ожидаемый объект стиля:

```csharp
public partial class StudentRegistrationComponent : ComponentBase
{
    public StyleBase StyleElement { get; set; }
    public StudentRegistrationStyle StudentRegistrationStyle { get; set; }
    ...
    protected override void OnInitialized() => SetupStyles();

    public void SetupStyles()
    {
        this.StudentRegistrationStyle = new StudentRegistrationStyle
        {
            SubmitButton = new SharpStyle
            {
                BackgroundColor = "blue"
            },
        };
    }
    ...
}
```

Затем на стороне разметки привяжем все свойства к соответствующим элементам:

```html
<StyleBase @ref=StyleElement
           Style=StudentRegistrationStyle />

<ButtonBase CssClass="submit-button" ... />
```

Наши тесты должны пройти, и это краткая демонстрация стандартизированного способа тестирования стилей для UI-компонентов.

#### 3.2.1.2.0.1.2 Действия (Actions)
Действия в основных компонентах очень похожи на действия в базовых компонентах или элементах. Однако важно понимать, что любое действие можно легко проверить либо путем изменения свойства или стиля, либо путем создания других компонентов, либо простым запуском других действий. Это также может быть комбинация одного или нескольких перечисленных вариантов. Например, кнопка отправки может изменять свойства существующих элементов, делая их неактивными, и одновременно инициировать вызов/действие в другом сервисе. Всё это должно быть проверяемым, как мы обсуждали выше.

##### 3.2.1.2.0.1.0 Полная реализация и тесты
Разберем реализацию основного компонента.
```csharp
public partial class StudentRegistrationComponent : ComponentBase
{
    [Inject]
    public IStudentViewService StudentViewService {get; set;}

    public StudentRegistrationComponentState State {get; set;}
    public StudentView StudentView {get; set;}
    public TextBoxBase StudentNameTextBox {get; set;}
    public ButtonBase SubmitButton {get; set;}
    public LabelBase StatusLabel {get; set;}

    public void OnInitialized() =>
        this.State == StudentRegistrationComponentState.Content;

    public async Task SubmitStudentAsync()
    {
        try
        {
            this.StudentViewService.AddStudentViewAsync(this.StudentView);
        }
        catch (Exception exception)
        {
            this.State = StudentRegistrationComponentState.Error;
        }
    }
}
```
Приведенный выше код показывает различные типы свойств внутри любого компонента: зависимый вью-сервис сопоставляет необработанные модели/данные API в потребляемые модели UI. `State` определяет, должен ли компонент находиться в состоянии загрузки (`Loading`), контента (`Content`) или ошибки (`Error`). Вью-модель данных связывает входящий ввод с одной унифицированной моделью `StudentView`. Последние три — это базовые компоненты, используемые для построения формы регистрации.

Посмотрим на сторону разметки основного компонента:
```html
<Condition Evaluation=IsLoading>
    <Match>
        <LabelBase @ref=StatusLabel Value="Загрузка ..." />
    </Match>
</Condition>

<Condition Evaluation=IsContent>
    <Match>
        <TextBoxBase @ref=StudentNameTextBox @bind-value=StudentView.Name />
        <ButtonBase @ref=SubmitButton Label="Отправить" OnClick=SubmitStudentAsync />
    </Match>
</Condition>

<Condition Evaluation=IsError>
    <Match>
        <LabelBase @ref=StatusLabel Value="Произошла ошибка" />
    </Match>
</Condition>
```

Мы связали ссылки на свойства компонента регистрации студентов с UI-компонентами, чтобы обеспечить рендеринг этих компонентов и выполнение оправки данных.

Компонент имеет состояния уже загруженного контента и состояния после отправки. Рассмотрим пару тестов для их проверки.

```csharp
[Fact]

{

        StudentRegistrationComponentState.Content;
```

Этот тест подтвердит, что всем компонентам назначено ссылочное свойство и что не было сделано никаких вызовов внешних зависимостей. Он также подтвердит, что код в функции `OnInitialized` на уровне компонента валиден и работает как ожидается.

Теперь посмотрим на валидацию кода отправки:

```csharp
[Fact]
public void ShouldSubmitStudentAsync()
{
    // given
    StudentRegistrationComponentState expectedComponentState =
```

Тест выше подтверждает, что при отправке модель студента заполняется данными, установленными программно через экземпляр базового компонента, и проверяет, что все эти компоненты отображаются на экране перед конечными пользователями, проверяя наличие назначенного экземпляра у каждого базового компонента во время выполнения или рендеринга.

##### 3.2.1.2.0.1.1 Ограничения
Основные компоненты имеют те же ограничения, что и базовые, поскольку они не могут вызывать друг друга на этом уровне. Существует уровень оркестрирующих основных компонентов (Orchestration Core Components), которые могут объединять несколько компонентов для обмена сообщениями. Тем не менее, они не отрисовывают ничего самостоятельно, так же как оркестрирующие сервисы делегируют всю работу своим зависимостям.

Один вью-сервис соответствует одному основному компоненту, который отрисовывает одну и только одну вью-модель. Кроме того, основным компонентам не разрешено вызывать более одного вью-сервиса. И в этом они всегда остаются верны вью-модели.

Вью-сервисы могут выполнять свою работу на уровне оркестрации в чрезвычайно сложном потоке, но мы рекомендуем сохранять всё на плоском уровне. Эти же вью-сервисы выполняют только маппинг, добавление полей аудита и базовые структурные валидации.

#### 3.2.1.2.0.2 Страницы (Pages)
В каждом веб-приложении страницы являются фундаментальным обязательным контейнерным компонентом, который должен существовать, чтобы конечные пользователи могли осуществлять навигацию. Страницы в основном содержат маршрут, передают параметр этого маршрута и объединяют компоненты основного уровня для представления бизнес-ценности.

Отличным примером страницы является дашборд. Страницы дашборда содержат несколько компонентов, таких как плитки, уведомления, заголовки и боковые панели, которые ссылаются на другие страницы. Страницы не содержат никакой бизнес-логики сами по себе, а делегируют все операции, связанные с маршрутом, своим дочерним компонентам.

Разберем простую реализацию страницы:

```html
@page "/registration"

<HeaderComponent />
<StudentRegistrationComponent />
<FooterComponent />
```

Страницы намного проще основных или базовых компонентов. Они не требуют модульного тестирования и им не обязательно нужен код бэкенда. Они чисто ссылаются на свои компоненты без ссылок (если не требуется) и помогают обслуживать этот контент при навигации через маршрут.

Страницы организованы в каталоге `Views/Pages`, при этом каждая страница находится в папке, специфичной для предметной области. Например:

- `Views/Pages/Subscriptions/SubscriptionsPage.razor`
- `Views/Pages/Users/UsersPage.razor`
- `Views/Pages/Groups/GroupsPage.razor`

#### 3.2.1.2.0.3 Ненавязчивость (Unobtrusiveness)
Нарушением считается включение кода из нескольких технологий/языков на одной странице для всех UI-компонентов. Например, код стилей CSS, код C# и HTML-разметка не могут существовать в одном файле. Они должны быть разделены по своим собственным файлам.

Правило ненавязчивости помогает предотвратить когнитивное загрязнение для инженеров, создающих UI-компоненты, и делает систему гораздо более простой в обслуживании. Вот почему каждый компонент может включать в себя вложенные файлы, если IDE/среда разработки поддерживает частичные (partial) реализации:

- StudentRegistrationComponent.razor
    - StudentRegistrationComponent.razor.cs
    - StudentRegistrationComponent.razor.css

Основной файл `.razor` содержит всю разметку, необходимую для инициализации компонента. В то же время оба вложенных файла являются вспомогательными для простого кода логики UI и стилизации. Такой уровень организации (особенно в Blazor) не требует никаких ссылок для этих вложенных/вспомогательных файлов. Тем не менее, это может быть не так для других технологий, поэтому я призываю инженеров делать все возможное, чтобы соответствовать этой модели/Стандарту.

#### 3.2.1.2.0.4 Организация (Organization)
Все UI-компоненты перечислены в папке `Views` внутри решения. Давайте посмотрим:

- Views
    - Bases
        - Buttons/ButtonBase.razor
        - Toasts/ToastBase.razor
        - Divisions/DivisionBase.razor
    - Components
        - Foundations
            - Subscriptions/SubscriptionsComponent.razor
        - Processings
            - UserGrids/UserGridsProcessingComponent.razor
        - Orchestrations
            - GroupDialogs/GroupDialogsOrchestrationComponent.razor
    - Pages
        - Subscriptions/SubscriptionsPage.razor
        - Users/UsersPage.razor
        - Groups/GroupsPage.razor

Такая организация, соответствующая триединой природе («tri-nature»), должна облегчить перенос переиспользуемых компонентов и их поиск по категориям. С учетом вложенности я оставляю на усмотрение инженеров решение о том, стоит ли далее разбивать эти компоненты по папкам/пространствам имен или оставлять их на одном уровне.
