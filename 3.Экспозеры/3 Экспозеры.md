# 3 Экспозеры

## 3.0 Введение

Экспозеры — это одноразовые компоненты в любой системе, которые раскрывают функциональность основной бизнес-логики, отображая её ответы в конкретный протокол. Например, в RESTful-коммуникации контроллер API отвечает за возврат кода `200` при успешном ответе. То же самое применяется к другим протоколам — gRPC, SOAP и любым другим протоколам взаимодействия между распределёнными системами.

Компоненты-экспозеры похожи на брокеры. Они являются последней точкой контакта между основной бизнес-логикой и внешним миром. Они создаются с намерением, что в какой-то момент могут быть отключены от текущей системы, позволяя той же основной логике интегрироваться с современными системами, протоколами или интерфейсами.

## 3.0.0 Назначение

В целом, основная ответственность компонентов экспозиции — позволить кому-либо или чему-либо взаимодействовать с вашей бизнес-логикой. Для этой цели необходимо аккуратно сопоставить с потребителем каждый возможный ответ основной бизнес-логики. Слово «аккуратно» здесь не случайно: иногда конкретные внутренние проблемы системы не должны раскрываться во внешний мир.

Такое отображение ответов может быть совершенно незатратным, если протокол и язык, на котором говорит ваша бизнес-логика, совпадают с технологиями потребителя. Однако бывают случаи, когда внешний протокол не совпадает точно с ответом системы. В этом случае ответственность за двусторонний маппинг ложится на компонент-экспозер. Контроллеры API — отличный пример: они возвращают код `4xx` при исключениях валидации и десериализованный JSON при успехе.

### 3.0.0.0 Чистый маппинг

Важнейший аспект компонентов экспозиции: им **запрещено** взаимодействовать с брокерами любого типа. Им также **запрещено** содержать какую-либо бизнес-логику — никакой последовательности вызовов, итераций или условных решений. Точно так же, как брокеры лишь соединяют существующий мир с внешним, экспозеры являются мостом в обратную сторону.

## 3.0.1 Типы компонентов экспозиции

Компоненты экспозиции бывают трёх типов: протоколы связи, пользовательские интерфейсы и компоненты ввода/вывода.

### 3.0.1.0 Протоколы связи

Компонент экспозиции, представляющий собой протокол связи, может варьироваться от простых RESTful API до SOAP или gRPC. Это может быть и простой клиент в библиотеке, где потребители просто устанавливают библиотеку и взаимодействуют с вашей логикой через клиентские API.

Отличительная черта такого типа — событийная модель: компонент запускается входящим сообщением и отвечает ответом любого вида. Протоколы связи обычно предназначены для взаимодействия систем между собой, хотя могут быть доступны и понятны людям для тестирования и отладки.

### 3.0.1.1 Пользовательские интерфейсы

Другой тип компонентов экспозиции — пользовательские интерфейсы: от веб-, мобильных и десктопных приложений до простых командных строк. Они нацелены прежде всего на конечных пользователей, хотя могут автоматизироваться другими системами через интерфейсы командной строки.

Интерфейсы «человек-машина» (HMI) — кнопки на телефоне, клавиатуры, различные аппаратные компоненты — также могут относиться к этому уровню. То же применяется к компонентам «Интернета вещей» (IoT).

### 3.0.1.2 Компоненты ввода/вывода

Некоторые компоненты экспозиции не взаимодействуют ни с другой системой, ни с человеком. Это демоны или компоненты на основе ввода/вывода, выполняющие работу в фоновом режиме без триггера — как правило, на основе времени. Они могут использовать существующие протоколы или напрямую взаимодействовать с основной бизнес-логикой.

## 3.0.2 Единственная точка контакта

Компоненты экспозиции допускают взаимодействие **только с одним** сервисом. Интеграция с несколькими сервисами превратила бы экспозер в оркестрирующий или агрегирующий сервис, которым не место в уровне экспозиции.

Правило единственной точки контакта также обеспечивает лёгкую заменяемость самого компонента-экспозера: минимальные зависимости означают, что его можно переключить на любой протокол с наименьшими усилиями.

## 3.0.3 Примеры

Рассмотрим API-контроллеры как пример реального компонента экспозиции:

```csharp
[HttpPost]
public async ValueTask<ActionResult<Student>> PostStudentAsync(Student student)
{
    try
    {
        Student registeredStudent =
            await this.studentService.RegisterStudentAsync(student);

        return Created(registeredStudent);
    }
    catch (StudentValidationException studentValidationException)
        when (studentValidationException.InnerException is AlreadyExistsStudentException)
    {
        return Conflict(studentValidationException.InnerException);
    }
    catch (StudentValidationException studentValidationException)
    {
        return BadRequest(studentValidationException.InnerException);
    }
    catch (StudentDependencyException studentDependencyException)
    {
        return InternalServerError(studentDependencyException);
    }
    catch (StudentServiceException studentServiceException)
    {
        return InternalServerError(studentServiceException);
    }
}
```

Этот код демонстрирует API-метод, принимающий модель `Student` через HTTP POST. В ASP.NET контроллеры обеспечивают маппинг входящего JSON в модель `Student`, а затем отображают каждое категориальное исключение в соответствующий HTTP-статус.

## 3.0.4 Резюме

Компоненты экспозиции — это очень тонкие слои без интеллекта и логики. Они не оркестрируют несколько сервисов и не вызывают несколько компонентов основной бизнес-логики. Их единственная задача — двусторонний маппинг коммуникации между одной системой и другой.
