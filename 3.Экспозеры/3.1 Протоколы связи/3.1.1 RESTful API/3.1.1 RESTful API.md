# 3.1.1 RESTful API

## 3.1.1.0 Введение
Контроллеры RESTful API являются связующим звеном между слоем основной бизнес-логики и внешним миром. Они находятся на границе ядра любого приложения. В некотором смысле, API-контроллеры подобны брокерам: они обеспечивают успешную интеграцию нашей основной логики с остальным миром.

## 3.1.1.1 На карте
Контроллеры находятся на краю любой системы, независимо от того, является ли эта система монолитной платформой или простым микросервисом. Сегодня концепция API-контроллеров применяется даже к небольшим лямбда-выражениям или облачным функциям. Они выступают в роли триггера для доступа к системным ресурсам через REST.

Сторона потребителя контроллеров может быть разной. В промышленных системах это могут быть другие сервисы, запрашивающие данные из конкретной конечной точки. Это могут быть библиотеки-обертки над API, предоставляющие локальный доступ к внешним данным. Однако потребителями могут быть и инженеры, тестирующие эндпоинты и проверяющие их поведение с помощью инструментов вроде Swagger.

## 3.1.1.2 Характеристики
Реализация конечных точек RESTful API регулируется набором правил и принципов. Давайте обсудим их подробнее.

### 3.1.1.2.0 Язык
В реализации своих методов контроллеры говорят на ином языке, нежели сервисы и брокеры. Например, если брокер, взаимодействующий с хранилищем, использует терминологию вроде `InsertStudentAsync`, а соответствующий сервис — `AddStudentAsync`, то эквивалент в контроллере будет использовать RESTful-язык, например `PostStudentAsync`.

Стандартный контроллер использует лишь ограниченный набор терминов для выражения конкретных операций. Составим карту для наглядности:

| Контроллеры | Сервисы | Брокеры |
|-------------|---------|---------|
| Post        | Add     | Insert  |
| Get         | Retrieve| Select  |
| Put         | Modify  | Update  |
| Delete      | Remove  | Delete  |

Важно понимать, что эти операции могут быть расширены и адаптированы под конкретные нужды. Мы обсудим это чуть позже.
Язык, на котором говорят контроллеры, основан на HTTP-методах (HTTP Verbs). Их диапазон шире, чем вышеупомянутые CRUD-операции. Например, существует метод PATCH, позволяющий обновлять лишь отдельные части документа. По моему опыту, в современных промышленных приложениях PATCH используется редко, однако я могу расширить этот раздел в будущих версиях Стандарта.

#### 3.1.1.2.0.0 За пределами CRUD-процедур
Как упоминалось ранее, контроллер может взаимодействовать не только с фундаментальными сервисами. Они могут обращаться к функциям бизнес-логики более высокого порядка. Например, обрабатывающий сервис может предлагать процедуру `Upsert`. В этом случае обычный HTTP-метод не сможет адекватно описать комбинированную операцию вроде `Upsert`. Для таких ситуаций мы вводим пользовательские HTTP-методы.

Пользовательские HTTP-методы могут быть любыми, если они не конфликтуют с существующими и не содержат неподдерживаемых символов. Например, если система генерирует штрих-коды для товаров, процесс генерации не совсем вписывается в `POST` или `GET`. Особенно если учесть, что эти методы уже могут быть закреплены за тем же маршрутом для сохранения или получения штрих-кодов. В таком случае можно ввести новый метод `GENERATE`.

Мы реализовали эту возможность в библиотеке RESTFulSense, где метод контроллера определяется следующим образом:

```csharp
    [HttpCustom("GENERATE")]
    public ActionResult<Barcode> GenerateBarcode() =>
        this.barcodeProcessingService.Generate();
```
Клиент-потребитель может вызвать этот эндпоинт так:

```csharpsharp
    Barcode generatedBarcode =
        await restfulHttpClient.SendHttpRequestAsync<Student>(
            method: "GENERATE",
            relativeUrl: "api/barcodes",
            cancellationToken: someOrNoneCancellationToken);
```

Те же действия можно выполнить и без сторонних библиотек, используя нативный `HttpClient`.

#### 3.1.1.2.0.1 Похожие методы
Иногда, особенно при реализации базовых CRUD-операций, вам может потребоваться один и тот же HTTP-метод для разных процедур. Например, и `RetrieveById`, и `RetrieveAll` в мире RESTful разрешаются в метод `Get`. В этом случае каждая функция будет иметь уникальное имя и маршрут при сохранении одного и того же метода:

```csharp
[HttpGet]
public async ValueTask<ActionResult<IQueryable<Student>>> GetAllStudentsAsync()
{
    ...
}

[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    ...
}
```

Как видно выше, отличительными факторами здесь выступают имя функции (`GetAllStudents` против `GetStudentByIdAsync`) и маршрут (`Route`). Мы обсудим маршруты подробнее, но главный аспект — возможность реализации множества процедур с разными именами, даже если они используют один и тот же HTTP-метод.

#### 3.1.1.2.0.2 Соглашения о маршрутах
Доступ к контроллерам RESTful API осуществляется через маршруты. Маршрут — это просто URL-адрес в сочетании с HTTP-методом, позволяющий системе понять, какую процедуру вызвать. Например, если мне нужно получить студента с ID `123`, маршрут будет `api/students/123` с методом `GET`.

##### 3.1.1.2.0.2.0 Существительные и глаголы
Маршруты никогда не должны содержать глаголов. Это ответственность HTTP-метода. Например, именование маршрута `api/students/get` является нарушением соглашений Стандарта. Правило гласит: маршруты должны состоять из существительных, а HTTP-методы — это глаголы. Если используются настраиваемые методы, как упоминалось выше, для одного и того же маршрута может существовать бесконечное количество пользовательских методов.

Стандарт также навязывает принцип одного существительного. Маршруты не должны объединять несколько существительных в одно слово. Например, вместо `api/studentsubmissions` следует использовать `api/student-submissions`. 
В той же логике получение работ конкретного студента представляется так: `api/students/{studentId}/submissions`. Такое разделение необходимо, чтобы подчеркнуть пересечение ресурсов, а не просто выгрузку всего содержимого хранилища.

##### 3.1.1.2.0.2.1 Маршруты контроллеров
В приложении ASP.NET маршрут контроллера задается атрибутом в начале объявления класса:

```csharp
[ApiController]
[Route("api/[controller]")]
public class StudentsController
{
    ...
}
```

Здесь маршрут — это шаблон, определяющий, что эндпоинт начинается с `api` и продолжается именем класса без слова "Controller". Таким образом, `StudentsController` превращается в `api/students`. Все контроллеры должны использовать форму множественного числа контракта, который они обслуживают. В отличие от сервисов, где мы пишем `StudentService`, контроллеры будут во множественном числе — `StudentsController`.

##### 3.1.1.2.0.2.2 Маршруты для конкретных процедур/методов
Та же идея применима к методам внутри класса. Как показано в примере выше, мы пометили `GetStudentByIdAsync` атрибутом `HttpGet` с параметром, который добавляется к общему маршруту контроллера. Если маршрут контроллера `api/students`, то метод с `HttpGet("{studentId}")` даст итоговый маршрут `api/students/{studentId}`.

Затем `studentId` будет сопоставлен с входным параметром, имя которого *должно* совпадать с именем переменной в маршруте:

```csharp
[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    ...
}
```

Иногда эти маршруты содержат информацию о родительских ресурсах. Например, мы хотим создать библиотечную карточку для конкретного студента. Эндпоинт будет выглядеть как `api/students/{studentId}/librarycards` с методом `POST`. В этом случае мы должны четко различать эти входные параметры через правильное именование:

```csharp
[HttpPost("{studentId}/librarycards")]
public async ValueTask<ActionResult<LibraryCard>> PostLibraryCardAsync(Guid studentId, LibraryCard libraryCard)
{
    ...
}
```

##### 3.1.1.2.0.2.3 Множественное-Единственное-Множественное
При определении маршрутов важно следовать глобальным соглашениям. Общее правило: доступ к коллекции ресурсов -> выбор конкретной сущности -> снова доступ к коллекции ресурсов внутри этой сущности и так далее. Например: `api/students/{studentId}/librarycards/{librarycardId}`. Сначала мы обращаемся ко всем студентам, затем к конкретному ID, затем ко всем его карточкам и, наконец, к одной конкретной карте по её ID.

Это соглашение отлично работает для отношений «один ко многим». Но что делать с отношениями «один к одному»? Если у студента может быть только одна карточка, маршрут все равно будет выглядеть как `api/students/{studentId}/librarycards` с методом `POST`, и если карточка уже существует, должна вернуться ошибка `CONFLICT`.

##### 3.1.1.2.0.2.4 Параметры запроса и OData
Однако я рекомендую использовать плоские маршруты (flat-model routes), где каждый ресурс живет "сам по себе" со своими уникальными маршрутами. В нашем примере получение карточки конкретного студента будет выглядеть так: `api/librarycards?studentId={studentId}` или с использованием OData: `api/librarycards?$filter=studentId eq '123'`.

Пример реализации базовых параметров запроса:

```csharp
[HttpPost()]
public async ValueTask<ActionResult<LibraryCard>> PostLibraryCardAsync(Guid studentId, LibraryCard libraryCard)
{
    ...
}
```

Реализация на стороне OData:

```csharp
[HttpGet]
[EnableQuery]
public async ValueTask<IQueryable<LibraryCard>> GetAllLibraryCardsAsync()
{
    ...
}
```

Та же логика применима к `POST`. Вместо отправки на `api/students/{studentId}/librarycards`, мы можем использовать сам контракт и отправлять на `api/librarycards`, включая `studentId` внутрь модели. Идея плоских маршрутов упрощает реализацию и идеально соответствует общей философии Стандарта — сохранять простоту.

##### 3.1.1.2.0.2.5 Параметры X-WWW-Form-UrlEncoded
Стандарт предписывает концепцию одной сущности. Например, такой метод считается нарушением:
```csharp
ValueTask<Teacher> GetTeachersByStudentAsync(Student student);
```
Это нарушение, так как сервис здесь явно обрабатывает несколько типов сущностей. Однако Стандарт разрешает передачу примитивных параметров, таких как `string` или `bool`. Контроллеры поддерживают этот паттерн через параметры `x-www.form-urlencoded`:

На стороне контроллера:

```csharp
    [HttpPost("login")]
    [Consumes("application/x-www-form-urlencoded")]
    public async ValueTask<ActionResult<UserAuthentication>> PostLoginUserAsync(
        [FromForm] string username,
        [FromForm] string password)
    {
        ....
    }
```
На стороне потребителя:

```csharp
    var formUrlEncodedContent =
         new FormUrlEncodedContent(new[]
         {
            new KeyValuePair<string, string>("username", username),
            new KeyValuePair<string, string>("password", password)
         });
    
    HttpResponseMessage httpResponseMessage =
        await this.apiClient.ExecuteHttpCallAsync(this.httpClient.PostAsync(
            requestUri: $"{userAuthenticationsRelativeUrl}/login",
            content: formUrlEncodedContent));
```
Правило для сервисов применимо и к контроллерам: процедура на этом уровне не может принимать более 3 параметров. Если параметров больше, инженерам следует спроектировать систему так, чтобы она принимала полноценную сущность или модель и возвращала её же в ответе.

### 3.1.1.2.1 Коды и ответы
Ответы API-контроллера должны быть сопоставлены со статус-кодами. Например, если мы добавляем студента через `POST`, мы должны получить в ответ то же тело, что отправили, со статус-кодом `201` (`Created`).

Существует три основные категории ответов. Первая — успех (Success): и пользователь, и сервер выполнили свои задачи. Вторая — ошибки пользователя (User Error Codes, `4xx`): проблема в самом запросе. Третья — ошибки системы (System Error Codes, `5xx`): внутренняя или внешняя проблема на стороне сервера, требующая обращения в поддержку.

#### 3.1.1.2.1.0 Коды успеха (2xx)
Они указывают на то, что ресурс был успешно создан, обновлен, удален или получен. В некоторых случаях они означают, что запрос был успешно принят для обработки в режиме итоговой согласованности (eventual consistency).

| Код | Метод | Детали |
|-----|-------|--------|
| 200 | Ok | Для успешных операций GET, PUT и DELETE. |
| 201 | Created | Для успешных операций POST. |
| 202 | Accepted | Для задач, поставленных в очередь, результат которых пока неизвестен. |

Примеры:

В сценарии простого получения данных (не POST) лучше возвращать `Ok`:

```csharp
[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    Student retrievedStudent = 
        await this.studentService.RetrieveStudentByIdAsync(studentId);

    return Ok(retrievedStudent);
}
```

А при создании ресурса уместнее `Created`:

```csharp
[HttpPost]
public async ValueTask<ActionResult<Student>> PostStudentAsync(Student student)
{
    Student retrievedStudent = 
        await this.studentService.AddStudentAsync(student);

    return Created(student);
}
```

В случаях итоговой согласованности, когда ресурс еще не сохранен окончательно, мы ставим запрос в очередь и возвращаем `Accepted`:
```csharp
[HttpPost]
public async ValueTask<ActionResult<Student>> PostStudentAsync(Student student)
{
    Student retrievedStudent = 
        await this.studentEventService.EnqueueStudentEventAsync(student);

    return Accepted(student);
}
```

Правило Стандарта для таких случаев — предоставить отправителю некий токен, чтобы он мог проверить статус своего запроса через другой вызов API. Эти паттерны мы обсудим в другой книге — «Архитектура Стандарта» (The Standard Architecture).

#### 3.1.1.2.1.1 Коды ошибок пользователя (4xx)
Здесь запрос пользователя содержит ошибку, и система должна помочь понять, в чем именно проблема. Например, если ID студента невалиден, должен вернуться код `400` (`Bad Request`) с деталями проблемы.

Контроллеры отвечают за маппинг категориальных исключений основного слоя в соответствующие статус-коды:

```csharp
[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    try
    {
        ...
    }
    catch (StudentValidationException studentValidationException)
    {
        return BadRequest(studentValidationException.InnerException);
    }
}
```
Здесь мы перехватили категориальное исключение валидации и сопоставили его с `400`. Доступ к внутреннему исключению осуществляется для извлечения подробностей ошибки из свойства `Data`, которое содержит словарь всех отчетов об ошибках.

Иногда нужно копнуть глубже и перехватить конкретное локальное исключение. Например, `NotFoundStudentException` превращается в `404` (`NotFound`):

```csharp
[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    try
    {
        ...
    }
    catch (StudentValidationException studentValidationException)
        when (studentValidationException.InnerException is NotFoundStudentException)
    {
        return NotFound(studentValidationException.InnerException);
    }
}
```

Эта возможность проверки внутреннего типа исключения — преимущество процесса обертывания и развертывания (wrapping/unwrapping), описанного в разделе 2.3.3.0.2 Стандарта. Контроллер может проверять несколько типов внутри одного блока:

```csharp
    ...
    catch (StudentCoordinationDependencyValidationException studentCoordinationDependencyValidationException)
        when (studentValidationException.InnerException 
            is NotFoundStudentException
            or NotFoundLibraryCardException
            or NotFoundStudentContactException)
    {
        return NotFound(studentValidationException.InnerException);
    }
    ...
```

Распространенные сопоставления исключений:

| Код | Метод | Исключение |
|-----|-------|------------|
| 400 | BadRequest | ValidationException или DependencyValidationException |
| 404 | NotFound | NotFoundException |
| 409 | Conflict | AlreadyExistException |
| 423 | Locked | LockedException |
| 424 | FailedDependency | InvalidReferenceException |

Другие коды `4xx` могут генерироваться фреймворком автоматически (например, `401 Unauthorized` при наличии атрибута авторизации).

#### 3.1.1.2.1.2 Коды системных ошибок (5xx)
Они указывают на то, что потребитель не виноват. Произошло что-то серьезное на стороне системы, требующее вмешательства инженеров. Именно поэтому мы логируем такие исключения с соответствующим уровнем серьезности.

Наиболее частый код — `500` или `InternalServerError`:

```csharp
[HttpGet("{studentId}")]
public async ValueTask<ActionResult<Student>> GetStudentByIdAsync(Guid studentId)
{
    try
    {
        ...
    }
    ...
    catch (StudentDependencyException studentDependencyException)
    {
        return InternalServerError(studentDependencyException);
    }
}
```

По соображениям безопасности мы часто игнорируем детали внутреннего исключения в ответе, чтобы не раскрывать внутреннюю информацию сервера. Достаточно простого сообщения вроде «Произошла ошибка зависимости, обратитесь в службу поддержки». В идеале такие проблемы должны выявляться на этапе приемочных тестов.

| Код | Метод | Исключение |
|-----|-------|------------|
| 500 | InternalServerError | DependencyException или ServiceException |
| 507 | InsufficientStorage | InsufficientStorageException (только внутренние) |

Также бывает случай, когда команды договорились о контракте, но реализация еще не началась. Для таких пустых эндпоинтов подходит код `501 NotImplemented`.

Библиотека `RESTFulSense` помогает нам не только с более широким набором кодов, но и с сериализацией/десериализацией деталей проблем (problem details).

Мы будем рассматривать включение этих кодов в будущие версии Стандарта по мере необходимости.

### 3.1.1.2.2 Единственная зависимость
Компоненты экспозиции могут иметь ровно одну зависимость. И эта зависимость обязана быть Сервисом (Service). Ни брокеры, ни нативные зависимости здесь недопустимы.

Конструктор контроллера реализуется так:

```csharp
[ApiController]
[Route("api/[controller]")]
public class StudentsController : RESTFulController
{
    private readonly IStudentService studentService;

    public StudentsController(IStudentService studentService) =>
        this.studentService = studentService;

    ...
}
```

### 3.1.1.2.3 Единственный контракт
Это правило вытекает из принципа одной зависимости. Если сервисы работают только с одним контрактом, то и контроллеры следуют тому же правилу. Они могут принимать ID или запросы и возвращать этот контракт или список объектов этого контракта.

## 3.1.1.3 Организация
Контроллеры должны располагаться в папке `Controllers` и принадлежать к соответствующему пространству имен. При этом им не требуются собственные вложенные папки, так как их задача проста — экспозиция.

Пример пространства имен:

```csharp
namespace GitFyle.Core.Api.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class ContributionsController : RESTFulController
    {
        ...
    }
}
```

## 3.1.1.4 HomeController
Каждая система должна иметь эндпоинт, который мы называем `HomeController`. Его единственная задача — возвращать простое сообщение о том, что API "живо".

```csharp
using Microsoft.AspNetCore.Mvc;

namespace OtripleS.Web.Api.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class HomeController : ControllerBase
    {
        [HttpGet]
        public ActionResult<string> Get() =>
            Ok("Hello Mario, the princess is in another castle!");
    }
}
```

Этому контроллеру не нужна защита. Он открывает ворота для тестов «сердцебиения» (heartbeat tests), чтобы убедиться в работоспособности системы как сущности без проверки внешних зависимостей. Это критически важно, чтобы инженеры вовремя узнавали о падении системы.

## 3.1.1.5 Тесты
Существует три типа тестов для слоя экспозиции: модульные (unit), приемочные (acceptance) и интеграционные или сквозные (E2E). Для целей данной главы мы сосредоточимся на модульных и приемочных тестах.

### 3.1.1.5.0 Модульные тесты
Логика в контроллерах во многом схожа с логикой в сервисах — она заключается в маппинге исключений от зависимостей (или внутренних ошибок) в статус-коды для потребителя. Это и проверяется в модульных тестах.

Начнем с теста перед реализацией. Допустим, у нас есть `StudentsController`, который должен возвращать `200 OK` при успешном получении всех студентов.

Сначала определим сам класс контроллера (в черновом варианте):

```csharp
namespace School.Core.Api.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class StudentsController : RESTFulController
    {
        private readonly IStudentService studentService;

        public StudentsController(IStudentService studentService) =>
            this.studentService = studentService;
        
        [HttpGet]
        public async ValueTask<ActionResult<IQueryable<Student>>> GetAllStudentsAsync()
        {
            return NotImplemented(new NotImplementedException());
        }
    }
```
Здесь мы инициализировали контроллер, унаследовались от `RESTFulController` для поддержки статус-кодов и создали метод, возвращающий `NotImplemented`. Обратите внимание: на уровне контроллеров мы не пробрасываем само исключение (throw), а возвращаем соответствующий статус-код.

Теперь создадим класс тестов `StudentsControllerTests`:
```csharp
    public partial class StudentsControllerTests : RESTFulController
    {
        private readonly Mock<IStudentService> studentServiceMock;
        private readonly StudentsController studentsController;

        public StudentsControllerTests()
        {
            this.studentServiceMock = new Mock<IStudentService>();

            this.studentsController = new StudentsController(
                studentService: this.studentServiceMock.Object);
        }

        ....
    }
```
Основные моменты:
1. Класс `partial` — для разделения тестов на логические части.
2. Наследование от `RESTFulController` (из библиотеки `RESTFulSense`) для создания ожидаемых ответов вроде `Ok(retrievedStudents)`.
3. Мок зависимости, чтобы имитировать поведение сервиса.

Сам модульный тест для `GetAllStudentsAsync`:

```csharpsharp
    [Fact]
    public async Task ShouldReturnOkOnGetAllStudentsAsync()
    {
        // given
        List<Student> randomStudents =
            CreateRandomStudents();

        List<Student> returnedStudents =
            randomStudents;

        List<Student> expectedStudents =
            returnedStudents.DeepClone();

        OkObjectResult expectedObjectResult =
            Ok(expectedStudents);

        var expectedActionResult =
            new ActionResult<List<Student>>(
                expectedObjectResult);

        this.studentServiceMock.Setup(service =>
            service.RetrieveAllStudentsAsync())
                .ReturnsAsync(returnedStudents);

        // when
        ActionResult<List<Student>> actualActionResult =
            await this.studentsController
                .GetAllStudentsAsync();

        // then
        actualActionResult.ShouldBeEquivalentTo(
            expectedActionResult);

        this.studentServiceMock.Verify(service =>
            service.RetrieveAllStudentsAsync(),
                Times.Once);

        this.studentServiceMock.VerifyNoOtherCalls();
    }
```

Порядок действий здесь такой же, как в сервисах:
1. Создаем список случайных студентов для имитации ответа сервиса.
2. Клонируем его для ожидаемого результата.
3. Создаем объект `OkObjectResult` для имитации ожидаемого ответа контроллера.
4. Настраиваем мок сервиса.
5. Вызываем метод контроллера.
6. Сверяем реальный ответ с ожидаемым.
7. Проверяем, что метод сервиса был вызван ровно один раз и лишних вызовов не было.

Этот тест упадет, так как вместо `200 OK` он получит `501 Not Implemented`. Сделаем его успешным:

```csharp
namespace School.Core.Api.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class StudentsController : RESTFulController
    {
        private readonly IStudentService studentService;

        public StudentsController(IStudentService studentService) =>
            this.studentService = studentService;
        
        [HttpGet]
        public async ValueTask<ActionResult<IQueryable<Student>>> GetAllStudentsAsync()
        {
            List<Student> students =
                await this.studentService.RetrieveAllStudentsAsync();

            return Ok(students);
        }
    }
```
Теперь тест пройдет успешно.

### 3.1.1.5.1 Приемочные тесты
Пример приемочного теста:

```csharpsharp
[Fact]
public async Task ShouldPostStudentAsync()
{
    // given
    Student randomStudent = CreateRandomStudent();
    Student inputStudent = randomStudent;
    Student expectedStudent = inputStudent;

    // when 
    await this.otripleSApiBroker.PostStudentAsync(inputStudent);

    Student actualStudent =
        await this.otripleSApiBroker.GetStudentByIdAsync(inputStudent.Id);

    // then
    actualStudent.Should().BeEquivalentTo(expectedStudent);
    await this.otripleSApiBroker.DeleteStudentByIdAsync(actualStudent.Id);
}
```

Приемочные тесты должны охватывать каждый эндпоинт и отвечать за очистку тестовых данных. Ресурсы, не принадлежащие самому микросервису (например, база данных), должны имитироваться инструментами вроде `WireMock`.

В отличие от модульных тестов, приемочные пишутся «по факту»: эндпоинт должен быть уже полностью реализован и функционален.
