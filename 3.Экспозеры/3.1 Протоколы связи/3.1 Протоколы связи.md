# 3.1 Протоколы связи

## 3.1.0 Введение

В области экспозиции одной из наиболее распространённых методологий построения коммуникационной структуры между несколькими системами является использование протоколов связи. Эти протоколы эволюционировали на протяжении многих лет — от SOAP до REST и многих других протоколов, которые воплотились в технологиях для раскрытия API в распределённых системах.

В мире .NET технологии развивались вместе с архитектурой — от SOA на основе WCF до микросервисов на основе REST. Эволюция продолжается, но принципы меняются реже. В следующих главах мы рассмотрим наиболее распространённые протоколы связи со стандартизированным подходом к их реализации для приложений корпоративного уровня.

### 3.1.0.0 Принципы и правила

Протоколы связи обязаны решить две задачи при интеграции с основной бизнес-логикой: передачу результатов и отчётность об ошибках. Обсудим их кратко.

#### 3.1.0.0.0 Передача результатов

Любой протокол связи должен соответствовать принципу возврата результата основной бизнес-логики. Этот результат может быть сериализован в унифицированный формат (например, `JSON`) или передан как есть. В случае API-библиотек сериализация и десериализация данных обычно не требуется. Однако это ограничивает круг потребителей теми технологиями, которые могут интегрироваться с этими библиотеками.

Передача результатов также может сопровождаться статус-кодом. В RESTful API код `200` сопровождает возвращённый сериализованный `JSON`. Эти коды позволяют потребителям понять дальнейший план действий. Некоторые результаты вида `2xx` могут требовать отложенных действий, если ответ является `Accepted`, а не `Created`.

#### 3.1.0.0.1 Отчёты об ошибках

Основная бизнес-логика должна предоставлять подробный отчёт обо всех ошибках валидации в конкретном запросе. Ответственность протоколов связи — представить эти отчёты об ошибках в исходной форме или сериализовать их в формат, легко поддающийся десериализации и восстановлению до исходного типа исключения на стороне клиента.

Сериализованные отчёты об ошибках также должны иметь собственные коды, чтобы клиент знал о следующих действиях. Мы рекомендуем придерживаться стандартизированного способа сообщения об ошибках с документацией, которая помогает потребителям создавать лучшие клиенты для этих API.

### 3.1.0.1 Распространённые типы

Рассмотрим наиболее распространённые типы протоколов связи.

#### 3.1.0.1.0 REST

REST (Representational State Transfer) — это протокол с определёнными ограничениями, явно определяющими форму коммуникации, отчётность об ошибках и его принципиально stateless-природу. На момент написания данного Стандарта RESTful API являются наиболее распространённой формой коммуникации между распределёнными системами. RESTful API не зависят от технологий: любая технология или язык программирования могут их реализовывать, что позволяет им взаимодействовать без сохранения состояния и без жёстких зависимостей от выбора технологий клиентом или сервером.

#### 3.1.0.1.1 Библиотеки

Ещё одним распространённым протоколом связи являются API, реализованные в виде библиотек. Например, пакеты NuGet — это опубликованные и распространяемые библиотеки, которые позволяют разработчикам задействовать локализованную основную бизнес-логику или взаимодействовать с внешним ресурсом для достижения конкретной цели.

#### 3.1.0.1.2 Другие типы

Существует несколько других типов протоколов связи: как старые, например SOAP с его WCF, так и набирающие популярность — gRPC, GraphQL и другие.

Мы сосредоточимся главным образом на RESTful API как наиболее распространённом протоколе связи, кратко коснувшись и библиотек. По мере развития наши знания будут углубляться, и Стандарт будет включать всё больше различных протоколов связи и развиваться в части паттернов.

Начнём с RESTful API как протокола связи, а затем изучим различные аспекты компонента-экспозера.
