# 1 Брокеры

## 1.0 Введение
Брокеры — это посредники между бизнес-логикой и внешним миром.
Они представляют собой обёртки над внешними библиотеками, ресурсами, сервисами или API, реализующими локальный интерфейс, чтобы бизнес-логика могла взаимодействовать с ними без жёсткой привязки к конкретному ресурсу или реализации внешней библиотеки.

Брокеры по своей природе являются взаимозаменяемыми и одноразовыми — они создаются с пониманием того, что технологии постоянно развиваются и меняются. Поэтому в какой-то момент жизненного цикла приложения брокер будет заменён более современной технологией, лучше выполняющей поставленную задачу.

Вместе с тем брокеры обеспечивают возможность «подключения» бизнесу, абстрагируя конкретные зависимости от внешних ресурсов от того, что программное обеспечение пытается реализовать.

Например, если у вас есть API, созданный для потребления и предоставления данных с SQL-сервера, и в какой-то момент вы решили, что более выгодным вариантом для вашего API будет переход на технологию NoSQL — наличие брокера, снимающего зависимость от SQL, значительно упростит интеграцию с NoSQL с минимальными затратами времени и средств.

## 1.1 Положение на карте
В любом приложении — мобильном, настольном, веб-приложении или просто API — брокеры, как правило, находятся на «хвосте» приложения, поскольку они являются последней точкой контакта между нашим кодом и внешним миром.

Независимо от того, является ли внешний мир локальным хранилищем в памяти или независимой системой за API, в любом приложении они должны находиться позади брокеров.

## 1.2 Характеристики
Существует несколько простых правил, определяющих реализацию любого брокера:

### 1.2.0 Реализует локальный интерфейс
Брокеры должны соответствовать локальному контракту и реализовывать локальный интерфейс, чтобы обеспечить развязку между их реализацией и сервисами, которые их используют.

Например, если у нас есть локальный контракт `IStorageBroker`, требующий реализации любой CRUD-операции для локальной модели `Student`, контрактная операция будет выглядеть следующим образом:

```csharp
public partial interface IStorageBroker
{
    ValueTask<IQueryable<Student>> SelectAllStudentsAsync();
}
```

Реализация брокера хранилища будет выглядеть следующим образом:

```csharp
public partial class StorageBroker
{
    private DbSet<Student> Students { get; set; }

    public async ValueTask<IQueryable<Student>> SelectAllStudentsAsync() =>
        await SelectAllAsync<Student>();
}
```
Реализация локального контракта может быть заменена в любой момент: от использования Entity Framework (как в предыдущем примере) до применения совершенно иной технологии — например, Dapper — или полностью другой инфраструктуры, такой как база данных Oracle или PostgreSQL.

### 1.2.1 Без управления потоком выполнения
Брокеры не должны содержать никакого управления потоком выполнения: операторов `if`, циклов `while` или конструкций `switch`. Это связано с тем, что код управления потоком является бизнес-логикой, и ему место в слое сервисов, где должна располагаться бизнес-логика, а не в брокерах.

Например, метод брокера, извлекающий список студентов из базы данных, будет выглядеть примерно так:

```csharp
public async ValueTask<IQueryable<Student>> SelectAllStudentsAsync() =>
    await SelectAllAsync<Student>();
```
Это простая функция, вызывающая нативный `DbSet<T>` из EntityFramework и возвращающая локальную модель наподобие `Student`.


### 1.2.2 Без обработки исключений
Обработка исключений является формой управления потоком выполнения. Брокеры не должны обрабатывать исключения — они должны позволять им распространяться в сервисы, соседствующие с брокерами, где исключения могут быть корректно отображены и локализованы.


### 1.2.3 Собственная конфигурация
Брокеры также обязаны управлять своей конфигурацией — они могут получать зависимость через внедрение зависимостей от объекта конфигурации для получения и настройки параметров любого внешнего ресурса, с которым они интегрируются.

Например, строки подключения для взаимодействия с базой данных должны быть получены и переданы в клиент базы данных для установки успешного соединения:

```csharp
public partial class StorageBroker : EFxceptionsContext, IStorageBroker
{
    private readonly IConfiguration configuration;

    public StorageBroker(IConfiguration configuration)
    {
        this.configuration = configuration;
        this.Database.Migrate();
    }

    ...
    ...

    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    {
        optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
        string connectionString = this.configuration.GetConnectionString("DefaultConnection");
        optionsBuilder.UseSqlServer(connectionString);
    }
}
```

### 1.2.4 Нативные типы из примитивов
Брокеры могут конструировать объект внешней модели на основе примитивных типов, переданных сервисами, соседствующими с брокерами.

Например, в брокере уведомлений по электронной почте входные параметры функции `.Send(...)` требуют базовых входных данных: темы, содержимого или адреса. Пример:

```csharp
    public async ValueTask SendMailAsync(List<string> recipients, string subject, string content)
    {
        Message message = BuildMessage(recipients, ccRecipients, subject, content);
        await SendEmailMessageAsync(message);
    }
```

Примитивные входные параметры гарантируют отсутствие жёстких зависимостей между сервисами, соседствующими с брокерами, и внешними моделями.
Даже в ситуациях, когда брокер является простой точкой интеграции между вашим приложением и внешним RESTful API, настоятельно рекомендуется создавать собственные нативные модели, отражающие тот же JSON-объект, отправляемый или возвращаемый из API, вместо использования NuGet-библиотек, DLL-файлов или общих проектов для достижения той же цели.

### 1.2.5 Соглашения об именовании
Контракты брокеров должны оставаться как можно более обобщёнными, чтобы обозначать их общую функциональность; например, мы говорим `IStorageBroker` вместо `ISqlStorageBroker`, чтобы не привязываться к конкретной технологии или инфраструктуре.

При наличии единственного брокера хранилища сохранение того же имени для контракта и реализации будет удобнее. Однако в случае конкретных реализаций брокеров всё зависит от того, сколько брокеров предоставляют аналогичную функциональность. В нашем случае имеется конкретная реализация `IStorageBroker`, поэтому имя класса будет `StorageBroker`.

Если приложение поддерживает несколько провайдеров очередей, хранилищ или электронной почты, может потребоваться уточнение целевого назначения компонента; например, `IQueueBroker` может иметь несколько реализаций: `NotificationQueueBroker` и `OrdersQueueBroker`.

Однако если конкретные реализации работают с одной и той же моделью и бизнес-логикой, то более целесообразным может оказаться разграничение по технологии. В этом случае, например, для `IStorageBroker` могут существовать две конкретные реализации: `SqlStorageBroker` и `MongoStorageBroker`. Такой подход типичен в ситуациях, когда цель — снижение затрат на производственную инфраструктуру.

### 1.2.6 Язык
Брокеры «говорят» на языке поддерживаемых ими технологий.
Например, в брокере хранилища мы используем `SelectById` для соответствия SQL-оператору `Select`; в брокере очередей мы используем `Enqueue` для соответствия языку очередей.

Если брокер поддерживает конечную точку API, он должен следовать RESTful-семантике: `POST`, `GET` или `PUT`. Пример:

```csharp

public async ValueTask<Student> PostStudentAsync(Student student) =>
    await this.PostAsync(RelativeUrl, student);

```

### 1.2.7 Вверх и по горизонтали
Брокеры не могут вызывать другие брокеры, поскольку они являются первым уровнем абстракции и не нуждаются в дополнительных абстракциях или зависимостях, кроме модели доступа к конфигурации.

Брокеры также не могут иметь сервисы в качестве зависимостей, так как поток данных в любой системе должен идти от сервисов к брокерам, а не наоборот.

Например, даже когда микросервису необходимо подписаться на очередь, брокеры передают метод-прослушиватель для обработки входящих событий, но не вызывают сервисы, предоставляющие логику обработки.

Общее правило таково: только сервисы могут вызывать брокеры, а брокеры могут вызывать только внешние нативные зависимости.

### 1.2.8 Один ресурс — один брокер
Каждый брокер должен представлять ровно один ресурс. Например, если система интегрируется с базой данных SQL, должен существовать единственный брокер, отвечающий за хранение конфигурации и управление всеми взаимодействиями с этой базой данных.
Обратное также верно: брокер никогда не должен работать более чем с одним ресурсом, а один ресурс должен управляться только одним брокером.

## 1.3 Организация
Брокеры, поддерживающие несколько сущностей — например, брокеры хранилища, — должны использовать разделяемые классы (partial classes) для распределения ответственности по каждой сущности.

Например, если у нас есть брокер хранилища, предоставляющий все CRUD-операции как для модели `Student`, так и для модели `Teacher`, организация файлов должна быть следующей:

- IStorageBroker.cs
  - IStorageBroker.Students.cs
  - IStorageBroker.Teachers.cs
- StorageBroker.cs
  - StorageBroker.Students.cs
  - StorageBroker.Teachers.cs

Основная цель подобной организации с использованием разделяемых классов — разграничить ответственность по каждой сущности на более детальном уровне, что значительно повышает сопровождаемость программного обеспечения.

Соглашения об именовании файлов и папок брокеров строго ориентированы на множественное число сущностей, которые они поддерживают, и единственное число общего ресурса.

Например, мы говорим `IStorageBroker.Students.cs`. Также мы говорим `IEmailBroker` или `IQueueBroker.Notifications.cs` — ресурс в единственном числе, сущности во множественном.

Та же концепция применяется к папкам и пространствам имён, содержащим эти брокеры.

Например:

```csharp
namespace OtripleS.Web.Api.Brokers.Storages
{
    ...
}
```

И:
```csharp
namespace OtripleS.Web.Api.Brokers.Queues
{
    ...
}
```

## 1.4 Типы брокеров
В большинстве современных приложений для запуска корпоративного приложения обычно требуется ряд стандартных брокеров: брокеры хранилища, времени, API, логирования и очередей.

Некоторые брокеры взаимодействуют с существующими системными ресурсами, например со *временем*, что позволяет сервисам, соседствующим с брокерами, трактовать время как зависимость и управлять поведением конкретного сервиса в зависимости от значения *времени* в любой момент прошлого, настоящего или будущего.

### 1.4.0 Брокеры сущностей
Брокеры сущностей предоставляют точки интеграции с внешними ресурсами системы для выполнения бизнес-требований.

Например, брокеры сущностей интегрируются с хранилищем, предоставляя возможности для сохранения или извлечения записей из базы данных.

Брокеры сущностей также включают брокеры очередей, предоставляющие точку интеграции для помещения сообщений в очередь, которые другие сервисы будут потреблять и обрабатывать в рамках своей бизнес-логики.

Только сервисы, соседствующие с брокерами, могут вызывать брокеры сущностей, поскольку они требуют определённого уровня валидации получаемых или предоставляемых данных перед продолжением работы.

### 1.4.1 Вспомогательные брокеры
Вспомогательные брокеры — это брокеры общего назначения. Они предоставляют функциональность для поддержки сервисов, но не имеют характеристик, отличающих их от других системных компонентов.

Отличный пример вспомогательного брокера — `DateTimeBroker`: брокер, специально разработанный для абстрагирования бизнес-логики от жёсткой зависимости от системного времени.

Брокеры времени не ориентированы на конкретную сущность; они практически идентичны во многих системах.

Ещё один пример вспомогательных брокеров — `LoggingBroker`: они предоставляют данные в системы логирования и мониторинга, позволяя инженерам системы визуализировать общий поток данных и получать уведомления в случае возникновения проблем.

Вспомогательные брокеры могут вызываться на протяжении всего бизнес-слоя: в фундаментальных, обрабатывающих, оркестрирующих, координационных, управляющих или агрегирующих сервисах — в отличие от брокеров сущностей. Брокеры логирования необходимы как вспомогательный компонент системы, предоставляющий все возможности, необходимые сервисам для записи ошибок, вычисления даты или выполнения любой другой вспомогательной функции.

Реальные примеры брокеров можно найти в проекте OtripleS [здесь](https://github.com/hassanhabib/OtripleS/tree/master/OtripleS.Web.Api/Brokers).

## 1.5.1 Абстракция асинхронности
Для абстрагирования на операционном уровне все примеры реализаций в этом разделе используют тип `ValueTask` для обеспечения абстракции асинхронности.
Этот подход обеспечивает единообразную обработку асинхронных операций во всех реализациях методов, способствуя чистой и эффективной абстракции в соответствии с принципами Стандарта.

### Для StorageBroker.cs:
```csharp
using System;
using System.Linq;
using System.Threading.Tasks;
using EFxceptions.Identity;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using OtripleS.Web.Api.Models.Users;

namespace OtripleS.Web.Api.Brokers.Storages
{
    public partial class StorageBroker : EFxceptionsIdentityContext<User, Role, Guid>, IStorageBroker
    {
        private readonly IConfiguration configuration;

        public StorageBroker(IConfiguration configuration)
        {
            this.configuration = configuration;
            this.Database.Migrate();
        }

        private async ValueTask<T> InsertAsync<T>(T @object)
        {
            this.Entry(@object).State = EntityState.Added;
            await this.SaveChangesAsync();

            return @object;
        }

        private async ValueTask<IQueryable<T>> SelectAllAsync<T>() where T : class => this.Set<T>();

        private async ValueTask<T> SelectAsync<T>(params object[] @objectIds) where T : class =>
            await this.FindAsync<T>(objectIds);

        private async ValueTask<T> UpdateAsync<T>(T @object)
        {
            this.Entry(@object).State = EntityState.Modified;
            await this.SaveChangesAsync();

            return @object;
        }

        private async ValueTask<T> DeleteAsync<T>(T @object)
        {
            this.Entry(@object).State = EntityState.Deleted;
            await this.SaveChangesAsync();

            return @object;
        }

        ...

        protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
        {
            optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
            string connectionString = this.configuration.GetConnectionString("DefaultConnection");
            optionsBuilder.UseSqlServer(connectionString);
        }
    }
}
```

## 1.6 Резюме
Брокеры — это первый уровень абстракции между вашей бизнес-логикой и внешним миром. Однако они не являются единственным уровнем абстракции, поскольку некоторые нативные модели всё равно будут «протекать» через брокеры в сервисы, соседствующие с ними. Естественно избегать каких-либо отображений за пределами области логики, в нашем случае — фундаментальных сервисов.

Например, в брокере хранилища, независимо от используемой ORM, будут возникать нативные исключения вашей ORM (например, EntityFramework), такие как `DbUpdateException` или `SqlException`. В этом случае потребуется ещё один уровень абстракции, действующий как маппер между этими исключениями и нашей основной логикой для преобразования их в локальные модели исключений.

Эта ответственность лежит на сервисах, соседствующих с брокерами. Я также называю их фундаментальными сервисами; это последний уровень абстракции перед основной логикой, которая состоит из локальных моделей и контрактов.


## 1.7 Часто задаваемые вопросы
Со временем в процессе работы я столкнулся с рядом распространённых вопросов от инженеров. Поскольку некоторые из них повторялись неоднократно, их полезно собрать здесь, чтобы каждый мог познакомиться с различными точками зрения на брокеры.

### 1.7.0 Является ли паттерн Брокеров тем же, что и паттерн Репозитория?
С операционной точки зрения брокеры являются более универсальными, чем репозитории.

Репозитории, как правило, ориентированы на операции с хранилищем, главным образом с базами данных. Однако брокеры могут быть точкой интеграции с любой внешней зависимостью, например с сервисами электронной почты, очередями и другими API.

Паттерн, наиболее схожий с брокерами, — это паттерн «Единица работы» (Unit of Work). Он главным образом сосредоточен на общей операции, не привязывая определение или имя к конкретной операции.

В целом все эти паттерны пытаются реализовать одни и те же принципы SOLID: разделение ответственности, внедрение зависимостей и единственная ответственность.

Но поскольку SOLID — это принципы, а не точные руководства, ожидается, что различные реализации и паттерны для достижения этого принципа будут разными.

### 1.7.1 Почему брокеры не могут реализовать контракт для методов, возвращающих интерфейс вместо конкретной модели?
Это было бы идеальной ситуацией, однако это также потребовало бы от брокеров выполнения преобразования или маппинга между нативными моделями, возвращаемыми SDK внешних ресурсов или API, и внутренней моделью, соответствующей локальному контракту.

Выполнение этого на уровне брокера потребует введения бизнес-логики в эту область, что выходит за рамки назначения данного компонента.

Мы определяем бизнес-логику как любой целенаправленный последовательный, условный или итерационный код. Брокеры не покрываются юнит-тестами, так как не содержат бизнес-логики. Они могут быть частью приёмочных или интеграционных тестов, но не юнит-тестов — просто потому, что в них нет бизнес-логики.

### 1.7.2 Если брокеры являются уровнем абстракции от бизнес-логики, почему мы допускаем «утечку» внешних исключений через них на уровень сервисов?
Брокеры — лишь *первый* уровень абстракции, но не единственный. Сервисы, соседствующие с брокерами, отвечают за преобразование нативных исключений, возникающих в брокере, в более локальную модель исключений, которую можно обрабатывать и обрабатывать внутри области бизнес-логики.

Бизнес-логика проявляется на уровнях обработки, оркестрации, координации и агрегации, где все исключения, возвращаемые модели и операции являются локальными для системы.

### 1.7.3 Почему мы используем разделяемые классы для брокеров, работающих с несколькими сущностями?
Поскольку брокеры должны владеть своей конфигурацией, при наличии нескольких сущностей логичнее использовать разделяемые классы, чтобы избежать повторной настройки каждого брокера хранилища для каждой сущности.

Разделяемые классы — возможность языка C#, но аналогичное поведение должно быть реализуемо через наследование в других языках программирования.

### 1.7.4 Являются ли брокеры тем же, что и провайдеры (паттерн Provider)?
Нет. Провайдеры размывают границу между сервисами (бизнес-логика) и брокерами (интеграционный слой). Брокеры ориентированы на конкретные взаимозаменяемые компоненты в системе, тогда как провайдеры включают нечто большее.

### 1.7.5 Почему `ValueTask` предпочтительнее `Task` в реализациях, описанных в этом разделе?
`ValueTask` — это структура, представляющая задачу, возвращающую значение.
Это основанное на значении представление задачи, которое позволяет избежать выделения памяти в случаях, когда задача завершается синхронно.

Для абстрагирования на операционном уровне все примеры реализаций в этом разделе используют тип `ValueTask` для обеспечения абстракции асинхронности.
Этот подход обеспечивает единообразную обработку асинхронных операций во всех реализациях методов, продвигая чистую и эффективную абстракцию в соответствии с принципами Стандарта.
Применение `ValueTask` снижает выделение памяти в сценариях, где результат часто доступен немедленно, тем самым повышая производительность при сохранении ясности кода.

### 1.7.6 Почему и как я могу подавить предупреждения в файлах кода?
Предупреждения генерируются компилятором для оповещения о потенциальных проблемах в коде. Важно устранять эти предупреждения, чтобы обеспечить чистоту и надёжность кода.
Инженеры и разработчики могут устранять предупреждения, следуя рекомендациям компилятора. Это может включать изменение кода, рефакторинг или обновление зависимостей.

Важно регулярно проверять и устранять предупреждения в коде для поддержания его качества и бесперебойной работы приложения.

Один из способов устранения предупреждений в коде:
Для подавления предупреждения, выдаваемого IDE или компилятором, можно настроить файл `.csproj` с помощью элемента `<NoWarn>`.
Этот подход позволяет глобально отключить конкретные предупреждения в рамках всего проекта.

Например, добавление `<NoWarn>CS1998</NoWarn>` в элемент `<PropertyGroup>` файла `.csproj` подавит предупреждение CS1998, которое сигнализирует об асинхронном методе без операторов `await`. Если требуется подавить несколько предупреждений, их можно перечислить через запятую. Этот метод обеспечивает чистый и последовательный способ управления предупреждениями без разброса директив `#pragma warning` по всему коду.
```csharp
<Project Sdk="Microsoft.NET.Sdk.Web">

	<PropertyGroup>
		<TargetFramework>net8.0</TargetFramework>
		<Nullable>disable</Nullable>
		<ImplicitUsings>disable</ImplicitUsings>
        <WarningLevel>CS1998</WarningLevel>
	</PropertyGroup>
    ...
```
