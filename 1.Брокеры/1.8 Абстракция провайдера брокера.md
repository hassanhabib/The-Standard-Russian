# 1.8 Стандартизированные библиотеки абстракции провайдеров (SPAL)
В этой главе рассматриваются провайдеры, на которые могут опираться брокеры для выполнения определённых операций. Большинство брокеров используют внешние библиотеки или процедуры, не принадлежащие инженерам, разрабатывающим систему. Эти внешние библиотеки могут соблюдать или не соблюдать лучшие практики в области абстракции и тестирования.

Стандарт предписывает опираться на стандартизированные провайдеры при проектировании и разработке систем. Эти стандартизированные провайдеры должны обладать следующими характеристиками:

## 1.8.0 Расширяемость
Стандартизированные библиотеки абстракции провайдеров должны быть расширяемыми для поддержки большего числа внешних провайдеров. Например, библиотека, поддерживающая взаимодействие с базой данных SQL Server, должна быть достаточно расширяемой для поддержки работы с MongoDB, MariaDB или любыми другими провайдерами без каких-либо дополнительных затрат со стороны потребителей этих библиотек.

### 1.8.0.0 Настраиваемость
Чтобы стандартизированные библиотеки можно было использовать с несколькими провайдерами, они должны позволять инженерам настраивать их для работы с конкретным провайдером — локальным или удалённым. Например, библиотеки абстракции провайдеров можно настраивать следующим образом:

```csharp
public class StorageBroker
{
    private readonly IProviderAbstraction providerAbstraction;

    public StorageBroker()
    {
        this.providerAbstraction = new ProviderAbstraction();
        
        this.providerAbstraction.Configure(provider => 
            provider.UseSqlServer(connectionString: ....));
    }
}
```

Пример использования другого провайдера:

```csharp
public class StorageBroker
{
    private readonly IProviderAbstraction providerAbstraction;

    public StorageBroker()
    {
        this.providerAbstraction = new ProviderAbstraction();
        
        this.providerAbstraction.Configure(provider =>
            provider.UseMariaDb(connectionString: ....));
    }
}
```

## 1.8.1 Распределяемость
Библиотеки абстракции должны позволять нескольким инженерам публиковать расширения библиотеки. Библиотека не обязана содержать реализации всех провайдеров в одном бинарном файле. Вместо этого такие библиотеки должны предоставлять интерфейс или контракт, который все другие расширения обязаны реализовывать для поддержки конкретного провайдера.

Предположим, у нас есть основной стандартизированный контракт `Standard.Storages.Core`. Мы можем опубликовать библиотеку с именем `Standard.Storages.Sql`. Любой другой разработчик также может опубликовать `Standard.Storages.MongoDb` для поддержки того же интерфейса. Пример интерфейса:

```csharp
public interface IStorageProvider
{
    ValueTask<T> Insert(T @object);
    ValueTask<IQueryable<T>> SelectAll();
    ...
    ...
    void Configure(Options options);
}
```
Возможности этого контракта должны представлять собой минимум, который любой провайдер способен предоставить. Однако дополнительные параметры в расширении провайдера могут открывать дополнительные возможности, которые могут отсутствовать в других библиотеках.

## 1.8.2 Внешняя имитируемость (Cloud-Foreign)
Стандартизированные библиотеки провайдеров должны обеспечивать взаимодействие с имитируемыми локальными «фантомными» API. Например, если система требует взаимодействия с очередью или шиной событий в облаке, библиотека провайдера, абстрагирующая эту технологию, должна обеспечивать локальное подключение для приёмочного тестирования и запуска в режиме «в самолёте» (Airplane Mode), который мы ранее обсуждали как принцип Cloud-Foreign.

Возможность внешней имитации может основываться на других внешних библиотеках, реализующих паттерны вроде PACT, для создания фантомных или поддельных экземпляров внешних API, запущенных на локальной машине или в сети. Пример:

```csharp
public class EventBroker
{
    private readonly IEventAbstractProvider eventAbstractProvider;

    public EventBroker(IConfiguration configuration)
    {
        this.eventAbstractProvider = 
            new EventAbstractProvider(
                configuration.Connection,
                configuration.TargetServerType);
    }
}
```
В приведённом фрагменте `TargetServerType` может принимать обязательные значения `Remote` (удалённый) или `Local` (локальный), однако инженеры, разрабатывающие библиотеку, могут добавить другие параметры по своему усмотрению.

Библиотеки абстрактных провайдеров должны точно воспроизводить поведение своих провайдеров. Например, в сценарии прослушивания очереди такие библиотеки должны предоставлять API с поддержкой событий для входящих сообщений, даже если они являются локальными, а не из внешнего сервиса (например, облачного).

Также допустимо предусмотреть возможность поддержки локальных интранет-сетей и управляемых сетей, не подключённых к публичному интернету, в конкретных сценариях с использованием тех же самых библиотек.

Стандартизированные библиотеки абстракции провайдеров — это подсистемы, которые должны иметь собственные слои Брокеров, Сервисов и Экспозиции в соответствии со Стандартом. Эти библиотеки ещё больше упростят разработку пользовательских систем: с чётко определёнными исключениями для обработки ожиданий и более простыми модификациями, поскольку они являются open-source и соответствуют Стандарту.

## 1.8.3 От локального к глобальному
Инженеры могут разрабатывать собственные локальные библиотеки абстракции провайдеров в рамках того же решения, предполагая, что им не удаётся найти существующее решение, удовлетворяющее их потребностям. При этом таким инженерам настоятельно рекомендуется открывать исходный код и публиковать проект абстракции для поддержки других инженеров в Сообществе Стандарта, у которых могут быть аналогичные потребности.

Такая практика поощряет инженеров повсеместно создавать коллективные усилия и паттерны «коллективного разума» для решения проблемы один раз и последующего распространения результата среди Инженерного Сообщества Стандарта для дальнейшего совершенствования и поддержки.

Соответствующие Стандарту граничные системы (пользовательские) более не должны добавлять в свои API, настольные или веб-приложения, или любые другие системы какие-либо нестандартные библиотеки.
