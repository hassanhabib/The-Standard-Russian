# 2 Сервисы

## 2.0 Введение

Сервисы, в целом, являются контейнерами для всей бизнес-логики в программном обеспечении — они представляют собой основной компонент любой системы и главный элемент, делающий одну систему непохожей на другую.

Наша главная цель в отношении сервисов — обеспечить их независимость от конкретных технологий или внешних зависимостей.

Любой бизнес-слой больше соответствует Стандарту, если он может подключаться к другим зависимостям и технологиям экспозиции с минимальными интеграционными усилиями.

### 2.0.0 Операции сервисов

Говоря о бизнес-логике, мы главным образом имеем в виду три основные категории операций: валидация, обработка и интеграция.

Рассмотрим каждую из этих категорий.

#### 2.0.0.0 Валидации

Валидации гарантируют, что входящие или исходящие данные соответствуют определённому набору правил: структурным, логическим или внешним — именно в таком порядке приоритета. Мы подробно обсудим это в следующих разделах.

#### 2.0.0.1 Обработка

Обработка главным образом сосредоточена на управлении потоком выполнения, маппинге и вычислениях для удовлетворения бизнес-потребности. Именно операции обработки отличают один сервис от другого и, в целом, одно программное обеспечение от другого.

#### 2.0.0.2 Интеграция

Наконец, процесс интеграции сосредоточен на извлечении или передаче данных из любых интегрируемых системных зависимостей или в них.

Мы подробно обсудим эти аспекты в следующей главе. Главное, что нужно понять о сервисах, — их проектирование строится на принципах «подключаемости» и настраиваемости, что позволяет им легко интегрироваться с любой технологией со стороны зависимостей и легко подключаться к любой функциональности экспозиции со стороны API.

### 2.0.1 Типы сервисов

Сервисы классифицируются по нескольким типам в зависимости от их роли в заданной архитектуре. Они делятся на три основные категории: валидаторы, оркестраторы и агрегаторы.

#### 2.0.1.0 Валидаторы

Сервисы-валидаторы — это главным образом сервисы, соседствующие с брокерами, или фундаментальные сервисы.

Основная ответственность этих сервисов — добавить уровень валидации поверх существующих примитивных операций (таких как CRUD-операции), чтобы гарантировать, что входящие и исходящие данные проходят структурную, логическую и внешнюю валидацию перед отправкой в систему или из неё.

#### 2.0.1.1 Оркестраторы

Сервисы-оркестраторы — это ядро слоя бизнес-логики. В зависимости от типа зависимостей они могут быть обрабатывающими, оркестрирующими, координационными или управляющими сервисами.

Сервисы-оркестраторы главным образом сосредоточены на объединении нескольких примитивных операций или нескольких операций бизнес-логики высокого порядка для достижения ещё более высокой цели.

Сервисы-оркестраторы являются:
- Лицами, принимающими решения в любой архитектуре.
- Владельцами управления потоком выполнения в любой системе.
- Главным компонентом, делающим одно приложение или программное обеспечение отличным от другого.

Мы намеренно проектируем сервисы-оркестраторы с расчётом на более длительное существование, чем любой другой тип сервисов в системе.

#### 2.0.1.2 Агрегаторы

Основная ответственность сервисов-агрегаторов — объединять результаты нескольких обрабатывающих, оркестрирующих, координационных или управляющих сервисов для предоставления единого API любому заданному контроллеру API или UI-компоненту для взаимодействия с остальной частью системы.

Агрегаторы — это привратники слоя бизнес-логики. Они гарантируют, что компоненты экспозиции данных (например, контроллеры API) взаимодействуют с системой через единственную точку контакта.

Агрегаторы, как правило, не заботятся о порядке вызова операций, привязанных к ним. Тем не менее иногда необходимо выполнить конкретную операцию — например, создать запись студента перед выдачей библиотечной карточки.

В следующих главах мы подробно рассмотрим каждый тип этих сервисов.

### 2.0.2 Общие правила

Ряд правил определяет общую архитектуру и проектирование сервисов в любой системе.

Эти правила обеспечивают общую читаемость, сопровождаемость и настраиваемость системы — именно в таком порядке приоритета.

#### 2.0.2.0 Делай или делегируй

Каждый сервис должен либо выполнять работу, либо делегировать её, но не делать и то, и другое одновременно.

Например, обрабатывающий сервис должен делегировать работу по сохранению данных фундаментальному сервису, а не пытаться делать это самостоятельно.

#### 2.0.2.1 Два-три (паттерн Флоренс)

Для сервисов-оркестраторов зависимости от сервисов (не брокеров) должны быть ограничены двумя или тремя — не одним, не четырьмя и не более.

Если оркестратор зависит только от одного сервиса, он нарушает определение оркестрации, подразумевающее объединение нескольких операций из разных источников для достижения более высокого уровня бизнес-логики.

Агрегаторы — единственный тип сервисов, которому разрешено нарушать это правило, поскольку комбинация и порядок вызовов сервисов не оказывают реального влияния.

Мы подробно обсудим паттерн Флоренс в следующих разделах Стандарта.

#### 2.0.2.2 Единственная точка экспозиции

Контроллеры API, UI-компоненты или любая иная форма экспозиции данных системы должны иметь единственную точку контакта с слоем бизнес-логики.

Например, конечная точка API, предоставляющая возможности для сохранения и извлечения данных студентов, не должна интегрироваться с несколькими сервисами — только с одним сервисом, предоставляющим все эти функции.

Иногда один оркестрирующий, координационный или управляющий сервис не предоставляет всего, что связано с конкретной сущностью. Сервис-агрегатор объединяет все эти функции в один сервис, готовый к интеграции с технологией экспозиции.

#### 2.0.2.3 Одинаковый или примитивный тип ввода/вывода

Все сервисы должны поддерживать единый контракт для возвращаемых и входных типов, за исключением примитивов.

Например, сервис, предоставляющий операции для типа сущности `Student`, не должен возвращать из каких-либо своих методов данные другого типа сущности.

Допустимо возвращать агрегацию той же самой сущности — встроенную или пользовательскую, например `List<Student>` или модель `AggregatedStudents` — либо примитивный тип, такой как количество студентов или булево значение, указывающее, существует ли студент. Но не контракт любого другого не-примитивного или не-агрегирующего типа.

Аналогичное правило распространяется на входные параметры: любой сервис может принимать входной параметр того же контракта, виртуального агрегирующего контракта или примитивного типа, но не любого другого контракта.

Это правило сосредотачивает ответственность сервиса на единственной сущности и всех связанных с ней операциях.

Когда сервис возвращает другой контракт, он нарушает соглашение об именовании — например, `StudentOrchestrationService`, возвращающий `List<Teacher>` — и попадает в ловушку, когда его начинают вызывать другие сервисы из совершенно иных конвейеров данных.

Если примитивные входные параметры принадлежат другой модели сущности, которая не является ссылкой на основную сущность, возникает вопрос об оркестрировании между двумя обрабатывающими или фундаментальными сервисами для поддержания единой модели без нарушения правила чистого контрактирования.

Если оркестрирующий сервис требует комбинации нескольких различных контрактов, новая унифицированная виртуальная модель сигнализирует о необходимости нового уникального контракта для оркестрирующего сервиса, при этом маппинги реализуются на конкретном уровне этого сервиса для обеспечения совместимости и безопасности интеграции.

#### 2.0.2.4 Каждый сервис — за себя

Каждый сервис отвечает за валидацию своих входных и выходных данных. Не следует полагаться на сервисы выше или ниже по цепочке в вопросе валидации данных.

Это механизм защитного программирования, гарантирующий, что при замене реализаций за контрактами ответственность любого заданного сервиса не будет затронута, если нижестоящие или вышестоящие сервисы по каким-либо причинам решат отказаться от своих валидаций.

В любой системе — монолитной, микросервисной или бессерверной — каждый сервис проектируется так, чтобы в какой-то момент быть отделённым от системы и стать последней точкой контакта перед интеграцией с каким-либо внешним брокером ресурсов.

Например, в следующей архитектуре сервисы отображают части входной модели `Student` в модель `LibraryCard`. Вот визуальное представление моделей:

###### Student

```csharp
public class Student
{
    public Guid Id {get; set;}
    public string Name {get; set;}
}
```

###### LibraryCard

```csharp
public class LibraryCard
{
    public Guid Id {get; set;}
    public Guid StudentId {get; set;}
}
```

Предположим, что наш оркестрирующий сервис `StudentOrchestrationService` гарантирует, что каждому новому зарегистрированному студенту будет выдана библиотечная карточка, поэтому логика может выглядеть следующим образом:

```csharp
public async ValueTask<Student> RegisterStudentAsync(Student student)
{
    Student registeredStudent =
        await this.studentProcessingService.RegisterStudentAsync(student);

    await AssignStudentLibraryCardAsync(student);

    return registeredStudent;
}

private async ValueTask<LibraryCard> AssignStudentLibraryCardAsync(Student student)
{
    LibraryCard studentLibraryCard = MapToLibraryCard(student);

    return await this.libraryCardProcessingService.AddLibraryCardAsync(studentLibraryCard);
}

private LibraryCard MapToLibraryCard(Student student)
{
    return new LibraryCard
    {
        Id = Guid.NewGuid(),
        StudentId = student.Id
    };
}
```

Как видно из примера, для успешного маппинга в `LibraryCard` требуется корректный идентификатор студента. Поскольку маппинг является ответственностью оркестратора, необходимо убедиться, что входной студент и его идентификатор корректны перед продолжением процесса оркестрации.

#### 2.0.2.5 Поток вперёд
Сервисы не могут вызывать сервисы того же уровня. Например, Фундаментальные сервисы не могут вызывать другие Фундаментальные сервисы, а Оркестрирующие сервисы не могут вызывать другие Оркестрирующие сервисы того же уровня.

##### 2.0.2.5.0 Для API
В силу фрактальности то же правило применяется к методам внутри этих сервисов. Публичные API не могут вызывать публичные API. Пример:

```csharp
public async ValueTask<Student> RetrieveStudentByIdAsync(Guid studentId)
{
    ...

    return await this.storageBroker.SelectStudentByIdAsync(studentId);
}

public async ValueTask<Student> ModifyStudentAsync(Student student)
{
    ...

    Student maybeStudent = 
        await this.storageBroker.SelectStudentByIdAsync(studentId);
    
    ...
    ...
}
```

В приведённом примере Фундаментального сервиса нельзя вызывать `RetrieveStudentByIdAsync` из публичного метода в другом публичном методе, таком как `ModifyStudentAsync`. Видно, что оба метода вызывают один и тот же метод из зависимости нижнего уровня, например `StorageBroker`, полностью независимо друг от друга.

Хотя это может показаться избыточным, причина в том, что публичные API, контракты или аналогичные конструкции рано или поздно устаревают. Они также могут быть полностью изменены с точки зрения реализации. Если публичный API зависит от другого публичного API того же уровня, устаревание одного вызовет каскадный эффект на все остальные. Это симптом хаотичного проектирования, которое Стандарт категорически запрещает.
