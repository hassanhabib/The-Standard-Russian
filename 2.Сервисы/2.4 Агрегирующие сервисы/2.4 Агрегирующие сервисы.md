# 2.4 Агрегирующие сервисы (Узел)

## 2.4.0 Введение

Основная ответственность агрегирующего сервиса — предоставить единственную точку контакта между слоем основной бизнес-логики и любыми слоями экспозиции. Он обеспечивает, чтобы несколько сервисов любой вариации разделяли один и тот же контракт для агрегации и экспозиции через один компонент экспозиции посредством одного логического слоя.

Агрегирующие сервисы не содержат никакой бизнес-логики. Они просто связывают несколько сервисов любого количества. Пример агрегирующего сервиса:

```csharp
public async ValueTask ProcessStudentAsync(Student student)
{
    await this.studentRegistrationCoordinationService.RegisterStudentAsync(student);
    await this.studentRecordsCoordinationService.AddStudentRecordAsync(student);
    ...
    ...
    await this.anyOtherStudentRelatedCoordinationService.DoSomethingWithStudentAsync(student);    
}
```

Агрегирующий сервис может иметь любое количество вызовов в любом порядке без ограничений. Агрегирующие сервисы должны быть чётко отделены от оркестрирующих сервисов или их вариаций.

## 2.4.1 Положение на карте

Агрегирующие сервисы всегда располагаются на другом конце слоя основной бизнес-логики — они являются последней точкой контакта между слоями экспозиции и логическими слоями.

## 2.4.2 Характеристики

Агрегирующие сервисы существуют главным образом тогда, когда несколько сервисов разделяют один и тот же контракт или примитивные типы одного контракта, требуя единственной точки экспозиции. Они существуют в высококомплексных приложениях, где нескольким сервисам необходима одна точка контакта.

### 2.4.2.0 Без ограничения зависимостей

В отличие от любого другого сервиса, агрегирующие сервисы могут иметь любое количество зависимостей при условии, что эти сервисы имеют одну и ту же вариацию. Например, агрегирующий сервис не может агрегировать оркестрирующий сервис и координационный сервис одновременно — это частичный паттерн Флоренс, где сервисы должны быть одной вариации, но не ограничены числом.

Зависимости агрегирующих сервисов не ограничены, поскольку сервис не выполняет никакой бизнес-логики между этими сервисами. Он лишь фокусируется на их экспозиции.

Пример теста агрегирующего сервиса:

```csharp
[Fact]
private async Task ShouldProcessStudentAsync()
{
    // given
    Student randomStudent = CreatedRandomStudent();
    Student inputStudent = randomStudent;

    // when
    await this.studentAggregationService.ProcessStudentAsync(inputStudent);

    // then
    this.studentRegistrationCoordinationServiceMock.Verify(service =>
        service.RegisterStudentAsync(student),
            Times.Once);

    this.studentRecordsCoordinationServiceMock.Verify(service =>
        service.AddStudentRecordAsync(student),
            Times.Once);
    ...

    this.anyOtherStudentRelatedCoordinationServiceMock.Verify(service =>
        service.DoSomethingWithStudentAsync(student),
            Times.Once);

    this.studentRegistrationCoordinationServiceMock.VerifyNoOtherCalls();
    this.studentRecordsCoordinationServiceMock.VerifyNoOtherCalls();
    ...
    this.anyOtherStudentRelatedCoordinationServiceMock.VerifyNoOtherCalls();
}
```

Мы проверяем и тестируем только аспект агрегации вызовов этих сервисов. В данном сценарии возвращаемый тип не требуется, но он может быть в транзитных сценариях.

Реализация приведённого теста:

```csharp
public async ValueTask ProcessStudentAsync(Student student)
{
    await this.studentRegistrationCoordinationService.AddStudentAsync(student);
    await this.studentRecordsCoordinationService.AddStudentRecordAsync(student);
    ...
    await this.anyOtherStudentRelatedCoordinationService.DoSomethingWithStudentAsync(student);    
}
```

### 2.4.2.1 Без валидации порядка

По определению, агрегирующие сервисы требуют вызова нескольких зависимостей без ограничений. Порядок вызова этих зависимостей также не является заботой агрегирующих сервисов — проверка порядка вызовов является основной бизнес-логикой, выходящей за рамки ответственности агрегирующего сервиса.

Нарушением Стандарта является использование таких техник, как `MockSequence`, для тестирования агрегирующего сервиса, а также проверка зависимости возвращаемого значения одного вызова от следующего.

### 2.4.2.2 Базовые валидации

Агрегирующие сервисы по-прежнему обязаны проверять, являются ли входящие данные структурно корректными на высоком уровне. Например, агрегирующий сервис, принимающий объект `Student`, проверит только то, не является ли `student` значением `null`. На этом всё.

Если нижестоящая зависимость требует передачи свойства входного параметра, также допускается структурная валидация этого значения свойства.

### 2.4.2.3 Транзитные операции (Pass-Through)

Агрегирующие сервисы могут также агрегировать, предлагая транзитные методы для нескольких сервисов:

```csharp
public partial class StudentAggregationService
{
    public async ValueTask<Student> AddStudentAsync(Student student)
    {
        ...
        return await this.studentCoordinationService.RegisterStudentAsync(student);
    }

    public async ValueTask<Student> AddStudentRecordAsync(Student student)
    {
        ...
        return await this.studentRecordsCoordinationService.AddStudentRecordAsync(student);
    }

    public async ValueTask<Student> DoSomethingWithStudentAsync(Student student)
    {
        ...
        return await this.anyOtherStudentRelatedCoordinationService.DoSomethingWithStudentAsync(student);
    }
}
```

### 2.4.2.4 Опциональность

Важно отметить, что агрегирующие сервисы являются опциональными. В отличие от фундаментальных сервисов, агрегирующие сервисы могут существовать или не существовать в архитектуре. Они существуют для решения проблемы абстракции — эта проблема может возникать или не возникать в зависимости от того, требует ли архитектура единственной точки экспозиции на границе слоя основной бизнес-логики.

### 2.4.2.5 Агрегация на уровне операций

Если агрегирующему сервису необходимо выполнить два разных вызова из одной и той же зависимости среди других вызовов, рекомендуется агрегировать их в отдельном private-методе:

```csharp
public async ValueTask ProcessStudentAsync(Student student)
{
    await this.studentCoordinationService.AddStudentAsync(student);
    await ProcessStudentRecordAsync(student);
}

private async ValueTask ProcessStudentRecordAsync(Student student)
{
    await this.studentRecordCoordinationService.AddStudentRecordAsync(student);
    await this.studentRecordCoordinationService.NotifyStudentRecordAdminsAsync(student);
}
```

### 2.4.2.6 Чистые контракты зависимостей

Важнейшее правило агрегирующего сервиса: его зависимости (в отличие от оркестрирующих сервисов) должны разделять один и тот же контракт. Входной параметр для любой публичной операции агрегирующего сервиса должен быть одним и тем же для всех его зависимостей.

## 2.4.3 Ответственности

Основная ответственность агрегирующего сервиса — предоставить единственную точку контакта между компонентами экспозиции и остальной основной бизнес-логикой.

### 2.4.3.0 Абстракция

Агрегирующий сервис успешно берёт на себя ответственность, когда его клиенты или потребители не имеют представления о том, что скрывается за строками его реализации. Например, агрегирующий сервис может объединять десятки различных сервисов и раскрывать единственную операцию в сценарии без ожидания ответа (fire-and-forget).

Агрегирующие сервисы скрывают любую идентификацию нижестоящих зависимостей от экспозеров любой ценой, делая интеграцию похожей на взаимодействие с единым сервисом, нативно предоставляющим все возможности.

### 2.4.3.1 Агрегация исключений

Агрегирующие сервисы похожи на оркестрирующие сервисы в части маппинга и агрегации исключений от нижестоящих зависимостей. Например, если `studentCoordinationService` выбрасывает `StudentCoordinationValidationException`, агрегирующий сервис отобразит это в `StudentAggregationDependencyValidationException`. Это соответствует концепции разворачивания и оборачивания локализованных исключений, детально рассмотренной в разделе 2.3.3.0.2 настоящего Стандарта.
